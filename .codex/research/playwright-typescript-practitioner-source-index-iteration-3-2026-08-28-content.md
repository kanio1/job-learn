### 2. Artem Bondar — Mock API responses

- Source: https://bondaracademy.com/blog/playwright-mock-api-response
- Retrieved: 2026-08-29
- Firecrawl status: complete

Mocking is the process of replacing dynamic data in your application with your own custom data. Instead of relying on real API responses, you intercept the network call and provide whatever response you need. In Playwright, this takes just a few lines of code.

Maybe you want to test an edge case that is difficult to set up using your real database. Loading 1,000 users just to check how pagination renders? That is a lot of work for one test. Or you have a slow API that keeps flaking your test environment and you want to eliminate that flakiness by controlling the response yourself. Or your application depends on a third-party API that is unreliable in the test environment. Mock just that one endpoint and your tests become stable and fast.

##### How API Mocking Works in Playwright

When your web application loads, it makes HTTP requests to backend APIs to fetch data. In the Conduit app, the homepage calls a `/api/tags` endpoint and an `/api/articles` endpoint.

Playwright sits between the browser and the network. With `page.route()`, you tell Playwright to watch for a specific URL pattern. When the browser tries to make that request, Playwright catches it before it reaches the server. Then, with `route.fulfill()`, you provide your own response. The browser gets your mock data as if it came from the real API.

This is also why mocking is instant. No network round-trip, no server processing, no database query.

##### How to Set Up API Mocking in Playwright

To mock an API response in Playwright, you need two methods: `page.route()` to intercept the request, and `route.fulfill()` to provide your custom response.

One important rule: **you must define the interception before the application makes the API call.** If your application makes API calls immediately on page load, your `page.route()` call must come before `page.goto()`.

```typescript
test('should display custom tags', async ({ page }) => {
  // Set up the mock BEFORE navigating
  await page.route('https://conduit-api.bondaracademy.com/api/tags', async route => {
    const tags = { tags: ['Artem', 'Bondar', 'YouTube'] };
    await route.fulfill({
      body: JSON.stringify(tags),
    });
  });
  // Now open the application
  await page.goto('https://conduit.bondaracademy.com/');
  // Verify the mocked data is displayed
  await expect(page.locator('.tag-list')).toContainText('Artem');
});
```

Notice the order. First, we tell Playwright what to intercept and what to respond with. Then we open the application.

Without the assertion at the end, the test finishes too quickly. Playwright disconnects the browser before the page even renders the mocked data. The `expect` assertion gives Playwright a reason to wait for the content to appear.

##### Mock API Response with Wildcard URL Patterns

Use wildcard patterns instead of the full API URL so your mock works across environments:

```typescript
await page.route('**/api/tags', async route => {
  const tags = { tags: ['Artem', 'Bondar', 'YouTube'] };
  await route.fulfill({
    body: JSON.stringify(tags),
  });
});
```

The `**/api/tags` pattern matches any URL that ends with `/api/tags`, regardless of the domain or protocol.

##### Store Mock Data in External Files

A better approach is to save mock data in separate JSON files and import them:

```json
// mocks/tags.json
{ "tags": ["Artem", "Bondar", "YouTube"] }
```

```typescript
import tags from '../mocks/tags.json';
test('should display custom tags', async ({ page }) => {
  await page.route('**/api/tags', async route => {
    await route.fulfill({
      body: JSON.stringify(tags),
    });
  });
  await page.goto('https://conduit.bondaracademy.com/');
  await expect(page.locator('.tag-list')).toContainText('Artem');
});
```

Your test file stays clean and your mock data lives in one place.

##### Conditional API Interception in Playwright

The `route.request()` method gives you access to details about the intercepted request. You can check the HTTP method, headers, or POST body before deciding what to do.

```typescript
await page.route('**/api/tags', async route => {
  if (route.request().method() === 'GET') {
    const tags = { tags: ['Artem', 'Bondar', 'YouTube'] };
    await route.fulfill({
      body: JSON.stringify(tags),
    });
  } else {
    await route.continue();
  }
});
```

GET requests to `/api/tags` return our mock data. POST, PUT, or DELETE requests continue to the real backend untouched.

You can also filter by POST body content:

```typescript
await page.route('**/api/articles', async route => {
  if (route.request().method() === 'POST' && route.request().postData()?.includes('draft')) {
    await route.fulfill({
      body: JSON.stringify({ article: { status: 'draft_saved' } }),
    });
  } else {
    await route.continue();
  }
});
```

##### When to Mock API Responses and When Not To

Do not overuse mocking. When you mock an API response, you are replacing the real integration between your frontend and backend with a fake one. If you mock too many endpoints, you might end up with a beautiful green test suite that misses a real defect.

When should you mock? Slow endpoints that cause flaky tests. Edge cases that are hard to set up with real data. Third-party APIs that are unreliable in test environments.

But your core business flows? Those should be real end-to-end tests. No mocking.

##### Final Thoughts

Mocking API responses in Playwright comes down to `page.route()` and `route.fulfill()`. Two methods, and you control what your application sees from the network. Wildcard patterns make your mocks portable across environments, external JSON files keep your code clean, and conditional logic lets you be precise about what gets intercepted.

Keep your core test automation flows real. Mock only where it actually helps.

### 3. Artem Bondar — Projects configuration

- Source: https://bondaracademy.com/blog/playwright-projects-configuration-guide
- Retrieved: 2026-08-29
- Firecrawl status: complete

When you install Playwright for the first time, you get three projects by default: Chromium, Firefox, and WebKit. This creates a false feeling that Playwright projects configuration is only about cross-browser testing. Not really true.

##### Do You Really Need Cross-Browser Testing?

Most engineers run their tests just in Chrome. Chrome holds roughly 70-80% of the browser market share. If your application works correctly in Chrome, it is very likely safe to release. Instead of spending resources on cross-browser execution, you can use projects for something that will actually help you organize your test suite.

##### How to Configure Playwright Projects for Test Groups

Remove the extra browsers and create two Chrome-based projects with different purposes:

```typescript
import { defineConfig, devices } from '@playwright/test';
export default defineConfig({
  projects: [
    {
      name: 'SmokeTests',
      use: { ...devices['Desktop Chrome'] },
      testMatch: /.*smoke.spec.ts/
    },
    {
      name: 'RegressionTests',
      use: { ...devices['Desktop Chrome'] },
      testIgnore: /.*smoke.spec.ts/
    },
  ],
});
```

The `SmokeTests` project uses `testMatch` to only run files matching `smoke.spec.ts`. The `RegressionTests` project uses `testIgnore` to run everything else. Target them from the command line:

```bash
npx playwright test --project=SmokeTests
```

##### How to Set Up Playwright Project Dependencies

You can create dependencies between projects. Say you want to run regression tests only if your smoke tests pass first:

```typescript
export default defineConfig({
  projects: [
    {
      name: 'SmokeTests',
      use: { ...devices['Desktop Chrome'] },
      testMatch: /.*smoke\.spec\.ts/,
    },
    {
      name: 'RegressionTests',
      use: { ...devices['Desktop Chrome'] },
      testIgnore: /.*smoke\.spec\.ts/,
      dependencies: ['SmokeTests'],
    },
  ],
});
```

If any smoke test fails, the regression project gets skipped entirely.

##### Data Setup and Teardown with Playwright Projects

Projects are not limited to running actual test files. You can create dedicated projects for data setup and cleanup:

```typescript
export default defineConfig({
  projects: [
    {
      name: 'DataSetup',
      testMatch: /.*data-load.setup.ts/,
      teardown: 'DataCleanup',
    },
    {
      name: 'SmokeTests',
      use: { ...devices['Desktop Chrome'] },
      testMatch: /.*smoke\.spec\.ts/,
      dependencies: ['DataSetup'],
    },
    {
      name: 'RegressionTests',
      use: { ...devices['Desktop Chrome'] },
      testIgnore: /.*smoke\.spec\.ts/,
      dependencies: ['SmokeTests'],
    },
    {
      name: 'DataCleanup',
      testMatch: /.*data-cleanup.setup.ts/,
    },
  ],
});
```

The execution chain: `DataSetup` runs first, `SmokeTests` next (dependent on `DataSetup`), `RegressionTests` after that (dependent on `SmokeTests`), and `DataCleanup` at the very end (configured as `teardown` for `DataSetup`).

You can also have multiple dependencies for a single project.

##### Per-Project Configuration in Playwright

Almost all framework properties can also be set at the project level. When you set them at the project level, they override the framework defaults.

Override parallel execution:

```typescript
export default defineConfig({
  fullyParallel: true,
  projects: [
    {
      name: 'SmokeTests',
      fullyParallel: false,
      testMatch: /.*smoke\.spec\.ts/,
    },
    {
      name: 'RegressionTests',
      testIgnore: /.*smoke\.spec\.ts/,
    },
  ],
});
```

Override workers, retries, and timeouts:

```typescript
{
  name: 'SmokeTests',
  retries: 0,
  timeout: 15000,
},
{
  name: 'RegressionTests',
  retries: 2,
  workers: 4,
  timeout: 60000,
},
```

Override use options per project:

```typescript
export default defineConfig({
  use: {
    baseURL: 'https://staging.example.com',
    trace: 'off',
  },
  projects: [
    {
      name: 'SmokeTests',
      use: {
        ...devices['Desktop Chrome'],
        baseURL: 'https://production.example.com',
        trace: 'on',
        viewport: { width: 1920, height: 1080 },
      },
    },
  ],
});
```

##### Framework-Level vs Project-Level Configuration

Not all properties are available at the project level. For example, `reporter` is a framework-level only property.

| Configuration | Framework Level | Project Level |
| --- | --- | --- |
| `fullyParallel` | Yes | Yes |
| `retries` | Yes | Yes |
| `timeout` | Yes | Yes |
| `workers` | Yes | Yes |
| `reporter` | Yes | **No** |
| `globalSetup` | Yes | **No** |
| `use.baseURL` | Yes | Yes |
| `use.viewport` | Yes | Yes |
| `use.trace` | Yes | Yes |

##### How to Run Playwright Projects from the Command Line

```bash
npx playwright test --project=SmokeTests
npx playwright test --project=RegressionTests
npx playwright test --project=SmokeTests --project=RegressionTests
```

When you trigger a project that has dependencies, Playwright automatically runs the dependency projects first.

##### Best Practices

Use descriptive names like `SmokeTests`, `RegressionTests`, `APITests`. Only create dependencies when the execution order truly matters. Keep setup/teardown projects focused on one thing.

### 4. Artem Bondar — Test PDF

- Source: https://bondaracademy.com/blog/how-to-test-pdf-in-playwright
- Retrieved: 2026-08-29
- Firecrawl status: complete

PDF testing comes up more often than you might think. Invoices, reports, export files — anything your application generates as a PDF will eventually need automated validation. Testing PDF files in Playwright is not complicated at all. You just need the right library.

##### Installing the pdf-parse Package

```bash
npm install pdf-parse --save-dev
```

##### Reading a PDF and Validating Text

A basic test that reads a PDF from a URL and prints its text content:

```typescript
import { test, expect } from '@playwright/test';
import pdf from 'pdf-parse';
test('read PDF content', async ({ request }) => {
  const response = await request.get('https://www.princexml.com/samples/invoice-plain/index.pdf');
  const body = await response.body();
  const result = await pdf(body);
  console.log(result.text);
});
```

We use Playwright `request` fixture to fetch the PDF, get the response body as a buffer, and pass it to `pdf()`. The `result.text` property contains the entire text content.

The simplest assertion checks that the text contains a specific value:

```typescript
expect(result.text).toContain('INV-2025-001');
```

##### Precise PDF Validation with Regular Expressions

To validate that `161126` belongs specifically to the "Invoice Number" field, use regular expressions. A regex pattern can match a specific portion of the text based on its surrounding context.

```typescript
const invoiceMatch = result.text.match(/Invoice Number:\s*(\d+)/);
expect(invoiceMatch![1]).toBe('161126');
```

The regex `/Invoice Number\s*(\d+)/` finds the text "Invoice Number," skips whitespace, and captures the next non-whitespace value. You can do the same for any field in the document.

##### Downloading and Validating a PDF in Playwright

The tricky part is timing. You need to start listening for the download event before clicking the button, otherwise you might miss it:

```typescript
const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Download PDF' }).click(),
]);
```

Read the data directly from the download stream without saving any files to disk:

```typescript
const buffer = await download.createReadStream().then(stream => {
  return new Promise<Buffer>((resolve, reject) => {
    const chunks: Buffer[] = [];
    stream.on('data', (chunk) => chunks.push(Buffer.from(chunk)));
    stream.on('error', reject);
    stream.on('end', () => resolve(Buffer.concat(chunks)));
  });
});
```

Pass this buffer to `PDFParse()` and make your assertions:

```typescript
const parser = new PDFParse({ data: buffer });
const result = await parser.getText();
const invoiceRegex = /Invoice number:\s*(\d+)/;
const match = result.text.match(invoiceRegex);
expect(match![1]).toBe('161126');
```

###### Full Test Example

```typescript
import { test, expect } from '@playwright/test';
import pdf from 'pdf-parse';

test('download and validate PDF', async ({ page }) => {
  await page.goto('https://playground.bondaracademy.com/pages/extra-components/pdf-download');

  const [download] = await Promise.all([
    page.waitForEvent('download'),
    page.getByRole('button', {name: 'Download PDF'}).click()
  ]);

  const buffer = await download.createReadStream().then(stream => {
    return new Promise<Buffer>((resolve, reject) => {
      const chunks: Buffer[] = [];
      stream.on('data', (chunk) => chunks.push(Buffer.from(chunk)));
      stream.on('error', reject);
      stream.on('end', () => resolve(Buffer.concat(chunks)));
    });
  });

  const parser = new PDFParse({ data: buffer });
  const result = await parser.getText();
  const invoiceRegex = /Invoice number:\s*(\d+)/;
  const match = result.text.match(invoiceRegex);
  expect(match![1]).toBe('161126');
});
```

Navigate, click, catch the download, read the stream, parse, assert. That is the whole thing.

### 5. Artem Bondar — Read Excel

- Source: https://bondaracademy.com/blog/how-to-read-excel-files-in-playwright
- Retrieved: 2026-08-29
- Firecrawl status: complete

The problem is simple. You have a login test with a hard-coded username and password. It works, but it only covers one scenario. What if you need to test with 10 different credentials? 50? Copy-pasting the same test is a maintenance nightmare.

The solution? Read your test data from an Excel file. Keep the data separate from the test logic, and anyone on the team can update inputs without touching the code.

##### Why Read Test Data from Excel Files?

Your spreadsheet can hold as many rows of credentials as you need, and the same test script handles all of them. You change data without changing code. You add new test cases by just adding rows to a spreadsheet. This is data-driven testing in Playwright in action.

##### Installing the xlsx NPM Package

The `xlsx` package on NPM has almost four million weekly downloads. It handles `.xlsx`, `.xls`, and `.csv` files out of the box.

```bash
npm install xlsx --save-dev
```

##### Reading Excel Data Step by Step

First, imports:

```typescript
import * as XLSX from 'xlsx';
import path from 'path';
```

Read the workbook and grab the worksheet:

```typescript
const userDataFile = path.join(__dirname, 'data', 'userdata.xlsx');
const workbook = XLSX.readFile(userDataFile);
const worksheet = workbook.Sheets['Sheet1'];
```

Convert the worksheet to JSON:

```typescript
const data = XLSX.utils.sheet_to_json(worksheet);
```

Each row becomes an object, and the column headers become the keys:

```json
[
  { "email": "user1@test.com", "password": "pass123" },
  { "email": "user2@test.com", "password": "pass456" }
]
```

##### Using Excel Data in Playwright Tests

Full working example:

```typescript
import { test, expect } from '@playwright/test';
import * as XLSX from 'xlsx';
import path from 'path';

const userDataFile = path.join(__dirname, 'data', 'userdata.xlsx');
const workbook = XLSX.readFile(userDataFile);
const worksheet = workbook.Sheets['Sheet1'];
const data = XLSX.utils.sheet_to_json(worksheet);

test('login with Excel data', async ({ page }) => {
  await page.goto('https://example.com/login');
  await page.getByLabel('Email').fill(`${data[0]['email']}`);
  await page.getByLabel('Password').fill(`${data[0]['password']}`);
  await page.getByRole('button', { name: 'Login' }).click();
});
```

Want to test with the second user? Change `data[0]` to `data[1]`. Want to loop through all users? Wrap it in a `for` loop or use `test.describe()` to generate a test for each row.

##### Adding TypeScript Type Safety

Create an interface that matches your spreadsheet columns:

```typescript
interface UserData {
  email: string;
  password: string;
}
```

Then pass it as a generic type parameter:

```typescript
const data = XLSX.utils.sheet_to_json<UserData>(worksheet);
```

TypeScript now knows exactly what fields each object has, so you get full IntelliSense support when accessing `data[0].email` or `data[0].password`.

### 6. Artem Bondar — Storage state

- Source: https://bondaracademy.com/blog/playwright-storage-state-authentication
- Retrieved: 2026-08-29
- Firecrawl status: complete

Imagine you have 50 or 100 test scenarios, and each starts with the same login flow. You are losing time and creating unnecessary pressure on your authentication system.

Playwright has a built-in solution for this. It is called **storage state**, and it lets you authenticate once, save the session, and reuse it across all your tests.

##### What is Playwright storage state authentication?

When you log into a web application, the browser stores your authenticated session using cookies, local storage, or IndexedDB. Playwright `storageState()` method captures that information and saves it to a JSON file. Then, every test that needs to be authenticated simply loads that file instead of going through the login flow again.

##### Step 1: Create the auth setup file

Create a file called `auth.setup.ts` in your tests directory:

```typescript
import { test as setup } from '@playwright/test';
const authFile = 'playwright/.auth/user.json';
setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByRole('textbox', { name: 'Email' }).fill('user@example.com');
  await page.getByRole('textbox', { name: 'Password' }).fill('password123');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForResponse('**/api/tags');
  await page.context().storageState({ path: authFile });
});
```

At the end, `page.context().storageState({ path: authFile })` saves the entire authenticated session into that JSON file. Cookies, local storage, all of it.

##### Step 2: Wait for the page to fully load

You need to ensure your application is fully loaded before capturing the storage state. If you grab the session too early, you might save an incomplete or invalid state.

Approaches:

```typescript
// Wait for a URL change
await page.waitForURL('/dashboard');

// Wait for a visible element
await page.getByRole('heading', { name: 'Welcome' }).waitFor();

// Wait for an API response
await page.waitForResponse('**/api/tags');
```

Pick whichever method makes sense for your app. Just do not skip this step.

##### Step 3: Configure playwright.config.ts

```typescript
import { defineConfig } from '@playwright/test';
export default defineConfig({
  projects: [
    {
      name: 'setup',
      testMatch: /auth\.setup\.ts/,
    },
    {
      name: 'chromium',
      use: {
        ...devices['Desktop Chrome'],
        storageState: 'playwright/.auth/user.json',
      },
      dependencies: ['setup'],
    },
  ],
});
```

The setup project runs first and generates the session file. The chromium project loads the saved session before every test, and the `dependencies` array makes sure setup completes before it starts.

##### Step 4: Simplify your tests

Before:

```typescript
test('create article', async ({ page }) => {
  await page.goto('/login');
  await page.getByRole('textbox', { name: 'Email' }).fill('user@example.com');
  await page.getByRole('textbox', { name: 'Password' }).fill('password123');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.getByText('New Article').click();
});
```

After:

```typescript
test('create article', async ({ page }) => {
  await page.goto('/');
  await page.getByText('New Article').click();
});
```

##### Do not forget the .gitignore

The `user.json` file contains sensitive information like access tokens and session cookies. Do not commit this file to your repository:

```
#### Playwright auth state
playwright/.auth/
```

##### Final Thoughts

Playwright storage state authentication takes five minutes to set up and saves you hours of test execution time. Authenticate once, reuse everywhere. The key is to wait for the page to fully load before capturing the state.

### 7. Artem Bondar — Data-driven testing

- Source: https://bondaracademy.com/blog/data-driven-testing-playwright
- Retrieved: 2026-08-29
- Firecrawl status: complete

Data-driven testing is when you take a single test scenario and run it against multiple sets of input data. Instead of writing separate test cases for every variation, you define your data in one place and let the framework iterate through it. Repeating the same test logic over and over is a maintenance nightmare. With data driven tests, you update the logic once and it applies to all your data sets.

##### The problem: duplicated test code

On the Conduit application, a sign up form has a username field that must be between 3 and 20 characters. That gives four test cases. The naive approach writes four separate tests with the same steps copy-pasted. Change a locator and you have to update all four tests.

##### How to create data-driven tests in Playwright

###### Create the dataset

In Playwright, you use a simple JavaScript array and put objects inside it. Each object is one test case with its own data:

```typescript
const testData = [
  { username: '12', errorMessage: 'username is too short', isErrorDisplayed: true },
  { username: '123', errorMessage: '', isErrorDisplayed: false },
  { username: '12345678901234567890', errorMessage: '', isErrorDisplayed: false },
  { username: '123456789012345678901', errorMessage: 'username is too long', isErrorDisplayed: true },
];
```

###### Loop with forEach

```typescript
testData.forEach(({ username, errorMessage, isErrorDisplayed }) => {
  test(`Error message test: ${username}`, async ({ page }) => {
    await page.getByText('Sign up').click();
    await page.getByPlaceholder('Username').fill(username);
    await page.getByPlaceholder('Email').fill('test@test.com');
    await page.getByPlaceholder('Password').fill('HelloWorld1');
    await page.getByRole('button', { name: 'Sign up' }).click();
    if (isErrorDisplayed) {
      await expect(page.locator('.error-messages')).toContainText(errorMessage);
    } else {
      await expect(page.locator('.error-messages')).not.toContainText(errorMessage);
    }
  });
});
```

The `if/else` block drives the `isErrorDisplayed` flag: when `true`, validate the error message; when `false`, validate it is NOT displayed.

###### Run and verify

You will see four separate test executions in the Playwright report, each with a unique name based on the username value.

##### Before and after

Before: four separate test blocks, around 32+ lines of mostly copy-pasted code. After: one dataset array and one test block inside a `forEach`, about 20 lines. Zero duplication.

##### When to use data-driven testing

Data-driven testing works best when your test scenarios follow the same flow but differ in input data and expected results. Think form validation with boundary values, search functionality with different terms, login scenarios with valid and invalid credentials, or API testing with different payloads and expected status codes.

### 8. Artem Bondar — AI agents review

- Source: https://bondaracademy.com/blog/playwright-ai-agents-review
- Retrieved: 2026-08-29
- Firecrawl status: complete

Playwright version 1.56 shipped with three AI-powered agents: Planner, Generator, and Healer. I spent a couple of hours testing all three agents on a real application, timed every operation, hit real bugs, and watched the AI hallucinate an entire test run that never happened.

##### What Are Playwright Agents, Really?

The reality? An agent is just a Markdown file with a set of instructions and a limited list of tools. Each agent lives under the `.github/chat-modes/` folder as an `.md` file.

The difference between an agent and a regular Copilot instruction is **tool exposure**. An agent only has access to specific tools. Why limit the tools? Security.

##### Planner Agent: Good for Brainstorming, Not for Planning

The Planner took **14 minutes and 18 seconds** and produced a 1,500-line Markdown file. The problem: the Planner had generated steps for fields and buttons it **never actually navigated to** during exploration. The agent was writing test cases based on knowledge it should not have had from the exploration alone. It also missed the most important validation scenario: you cannot create an article with a duplicate title.

When I narrowed the scope, the results got better, but then it got stuck updating the existing file. The Planner is useful for **brainstorming**. If you already have test cases and want to check for missing edge cases, feed your existing tests and the Planner output into an AI prompt and ask it to find the gaps. Do not rely on it as your primary test planning tool.

##### Generator Agent: Slower Than Codegen

**15 minutes and 40 seconds for two test cases.** The generated tests had the right structure but the assertions were rough, and both tests failed when I ran them.

The real problem: **Playwright Codegen is just faster and produces better results.** Playwright MCP only has access to the **accessibility tree** of your application. It cannot see the full DOM. No `data-test-id` attributes, no CSS selectors, no XPath. Codegen runs locally on your machine with no context limit, so it can inspect the entire DOM and produce reliable locators.

##### Healer Agent: The One I Actually Like

It took about **10 minutes to fix both tests**. The Healer ran each test in **debug mode** using a new MCP tool called `playwright_debug`, which collects console logs, network requests, and page snapshots during execution.

What did the Healer fix? It figured out that article titles need to be unique and added `Date.now()` to prevent conflicts. It replaced hardcoded values with variables. It found two "Edit Article" buttons on the page and scoped the selector to the first one. It replaced the meaningless snapshot assertion with an actual visibility check. After the Healer finished, both tests passed.

Debugging is often the most painful part of test automation. The Healer automates that process. Out of all three agents, this is the one I would actually use.

##### Which Playwright AI Agent Is Actually Worth Using?

| Agent | Time | Usefulness | Recommendation |
| --- | --- | --- | --- |
| Planner | 14+ min | Moderate | Good for brainstorming edge cases, not primary planning |
| Generator | 15+ min | Low | Use Playwright Codegen instead |
| Healer | ~10 min | High | Best of the three, use it for debugging |

##### Final Thoughts

Playwright AI agents are not magic. They are Markdown files with prompts and limited tool access. The Planner helps you brainstorm, the Generator is outperformed by Codegen, and the Healer earns its spot by using the debug tool to actually fix your failing tests. If you try one agent, make it the Healer.

### 9. Artem Bondar — Codegen recorder

- Source: https://bondaracademy.com/blog/playwright-codegen-test-recorder
- Retrieved: 2026-08-29
- Firecrawl status: complete

Playwright codegen is a built-in test generator that records your browser interactions and converts them into executable test scripts. You click buttons, fill forms, navigate pages, and codegen captures every action and translates it into proper Playwright syntax.

The recorder prioritizes user-facing locators like `getByRole()`, `getByText()`, and `getByLabel()` instead of brittle CSS selectors or XPath. So the generated code follows Playwright recommended locator strategy right out of the box.

##### Prerequisites: setting up the Playwright VS Code extension

Install the official Playwright Test for VS Code extension by Microsoft. After installation you see a new Test Explorer tab in the sidebar, and the **Record New** button is your entry point to the recorder.

##### Recording your first test with Record New

Click the **Record New** button. A new spec file is created and a blank Chromium browser window opens. Use the application like a real user would; the recorder captures everything and writes code into your spec file in real time.

The raw recording:

```typescript
import { test, expect } from '@playwright/test';
test('test', async ({ page }) => {
  await page.goto('https://conduit.bondaracademy.com/');
  await page.getByRole('link', { name: 'Sign in' }).click();
  await page.getByRole('textbox', { name: 'Email' }).click();
  await page.getByRole('textbox', { name: 'Email' }).fill('testgen@test.com');
  await page.getByRole('textbox', { name: 'Email' }).press('Tab');
  await page.getByRole('textbox', { name: 'Password' }).fill('test12345678');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.getByRole('link', { name: 'New Article' }).click();
  await page.getByRole('textbox', { name: 'Article Title' }).fill('Test title');
  await page.getByRole('textbox', { name: 'What\'s this article about?' }).fill('test description');
  await page.getByRole('textbox', { name: 'Write your article (in' }).fill('test body');
  await page.getByRole('button', { name: 'Publish Article' }).click();
  await page.getByRole('button', { name: 'Delete Article' }).first().click();
});
```

The recorder uses `getByRole()` whenever possible, but it also records steps we do not need, like clicking into input fields before filling them and pressing Tab between fields. The raw output always needs cleanup.

##### Cleaning up recorded tests

**Never use a recorded test as-is.** Remove unnecessary clicks before `fill()`, because Playwright `fill()` method automatically focuses the element. Remove Tab key presses between fields. Remove duplicate actions and overly specific locators.

After cleanup:

```typescript
import { test, expect } from '@playwright/test';
test('test', async ({ page }) => {
  await page.goto('https://conduit.bondaracademy.com/');
  await page.getByRole('link', { name: 'Sign in' }).click();
  await page.getByRole('textbox', { name: 'Email' }).fill('testgen@test.com');
  await page.getByRole('textbox', { name: 'Password' }).fill('test12345678');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.getByRole('link', { name: 'New Article' }).click();
  await page.getByRole('textbox', { name: 'Article Title' }).fill('Test title');
  await page.getByRole('textbox', { name: 'What\'s this article about?' }).fill('test description');
  await page.getByRole('textbox', { name: 'Write your article (in' }).fill('test body');
  await page.getByRole('button', { name: 'Publish Article' }).click();
  await page.getByRole('button', { name: 'Delete Article' }).first().click();
});
```

##### Adding steps with Record at Cursor

To extend a test without re-recording:

1. Temporarily remove the steps after the point where you want to insert new actions
2. Place your cursor at the insertion point in the code
3. Run the test so the browser stops at the right state
4. Click **Record at Cursor** in the Playwright extension panel

The recorder attaches to the already-open browser instance and inserts new actions exactly where your cursor is.

##### Adding assertions automatically

Recording actions is great, but tests without assertions are not really testing anything. The workflow: run your test up to the assertion point, click **Record at Cursor**, click the **Assert Text** button in the recorder toolbar, then click the element you want to assert.

```typescript
await expect(page.getByRole('heading')).toContainText('Test Title');
await expect(page.locator('app-article-page')).toContainText('hello world');
```

The recorder generates `toContainText()` by default, which is a partial match. Consider a more exact assertion like `toHaveText()` when you need to validate exact content.

##### Fixing imprecise locators in generated tests

The recorder does not always generate perfect locators, especially for assertions. `app-article-page` selects the entire article page section, not just the tag element. The fix is manual: right-click, Inspect, find the right selector.

```typescript
await expect(page.locator('.tag-list li')).toHaveText('hello world');
```

The recorder gives you a starting point, not a finished product. Always verify that locators are specific enough for your assertions.

##### Using codegen via the command line

```bash
npx playwright codegen https://your-app-url.com
```

This opens the Playwright Inspector alongside a browser window. The CLI approach does not write directly into a spec file; you copy the generated code manually. One place where the CLI shines is quick locator exploration.

##### Codegen recorder vs AI test generation

The Playwright codegen test recorder is faster for generating the initial layout of your tests. It captures real browser interactions with real locators on your actual application. It also has zero setup overhead. Both approaches give you a draft that needs review and cleanup. The recorder just gets you there quicker for standard UI flows.

##### Best practices

1. Always review and clean up after recording.
2. Verify locator accuracy, especially for assertions, which tend to be too broad.
3. Upgrade assertions when possible: `toContainText()` to `toHaveText()` after verifying the locator is precise enough.
4. Use Record at Cursor to extend tests.
5. Refactor after recording into page objects, reusable functions, or fixtures.
6. Do not record everything: write complex scenarios (API mocking, file uploads, multi-tab) manually.
7. Keep recordings short and focused.

### 10. Artem Bondar — GitHub Actions

- Source: https://bondaracademy.com/blog/playwright-github-actions-setup
- Retrieved: 2026-08-29
- Firecrawl status: complete

You have your Playwright tests running locally. But running tests on your machine is not enough. You need them running automatically on every push and every pull request. That is where GitHub Actions comes in.

##### Prerequisites

A GitHub account and Git installed (`git -v` to check).

##### Creating a GitHub Repository and Pushing Your Code

Create a new repository on GitHub, initialize Git in your project, create a first commit, point to the remote origin, and push. Then use VS Code Source Control to commit and sync all your project code.

##### Setting Up the GitHub Actions Workflow

Create the folder structure `.github/workflows/` and a file called `playwright.yaml`:

```yaml
name: Playwright Tests
on:
  push:
    branches: [ main, master ]
  pull_request:
    branches: [ main, master ]
jobs:
  test:
    timeout-minutes: 60
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: lts/*
    - name: Install dependencies
      run: npm ci
    - name: Install Playwright Browsers
      run: npx playwright install --with-deps
    - name: Run Playwright tests
      run: npx playwright test
    - uses: actions/upload-artifact@v4
      if: ${{ !cancelled() }}
      with:
        name: playwright-report
        path: playwright-report/
        retention-days: 30
```

The `on` section defines when tests run: every push to `main`/`master`, or a pull request targeting those branches. The job steps: check out code, set up Node.js, install dependencies, install Playwright browsers, run tests, upload the report as an artifact.

The browser installation step runs every time because the GitHub Actions runner is a fresh environment.

##### Running Your First CI Build

Push your changes and go to the **Actions** tab in your repository. Click the running job to view execution details.

If a test fails, seeing just "3 of 4 tests passed" does not give you much to work with. The answer is the **GitHub reporter**.

##### Adding the GitHub Reporter for Better Failure Insights

```typescript
export default defineConfig({
  reporter: [
    ['html'],
    ['github']
  ],
});
```

The `github` reporter is built specifically for GitHub Actions. It creates inline annotations directly in the GitHub UI when tests fail. After the build completes, the **Annotations** section on the Summary page shows the file where the failure happened, the exact assertion that failed, and expected versus received.

##### Rerunning Failed Jobs

On the GitHub Actions page for your workflow run, a dropdown offers **Rerun all jobs** and **Rerun failed jobs**. When you have multiple jobs, "Rerun failed jobs" saves time by skipping the ones that already passed.

##### Final Thoughts

Setting up Playwright on GitHub Actions is easy: create a workflow file, paste the config from the Playwright docs, add the GitHub reporter. GitHub Actions is completely free for public repositories. Your tests should not depend on someone remembering to run them.

### 11. Artem Bondar — Fix flaky tests

- Source: https://bondaracademy.com/blog/how-to-fix-playwright-flaky-tests
- Retrieved: 2026-08-29
- Firecrawl status: complete

A flaky test is a test that produces inconsistent results without any changes to the code. Flaky tests are dangerous because they train your team to ignore failures. In CI pipelines, they block pull requests and waste developer time. A test suite full of flaky tests is worse than no test suite at all, because it gives you false confidence.

##### Reason 1: Playwright Runs Faster Than Your Application

Playwright executes your test script faster than your application can update its state. Your test ends up interacting with stale data.

The problem, in a PetClinic application: click Edit on the first pet, change the name to "rabbit", click Update, verify the value:

```typescript
await page.getByRole('link', { name: 'Pet Types' }).click();
await page.getByRole('button', { name: 'Edit' }).first().click();
await page.getByRole('textbox').fill('rabbit');
await page.getByRole('button', { name: 'Update' }).click();
await expect(page.locator('[id="0"]')).toHaveValue('rabbit');
```

The assertion shows "cat" instead of "rabbit". Why? When you click the Edit button, an API call fetches the current pet name ("cat") to populate the field. Playwright does not know about that API call. It fills the field with "rabbit", then the API response overwrites it with "cat".

This test might pass 8 out of 10 times. On a fast machine the API returns before Playwright fills the field. On a slower CI server the timing shifts. That is what makes it flaky.

###### How to Debug It

Open the Playwright trace viewer:

```bash
npx playwright test --ui
```

Step through each action and look for moments where the page state changes unexpectedly between actions: Click Edit (before: empty), Fill "rabbit" (action: "rabbit" in the input), Click Update (**after: "cat" in the input**). That is the moment you catch it. The networking tab shows every API call, its timing, and its response.

###### Fix 1: Use Locator Assertions to Synchronize State

```typescript
await page.getByRole('link', { name: 'Pet Types' }).click();
await page.getByRole('button', { name: 'Edit' }).first().click();
// Wait for the existing value to load before replacing it
await expect(inputField).toHaveValue('cat');
await inputField.fill('rabbit');
await page.getByRole('button', { name: 'Update' }).click();
await expect(inputField).toHaveValue('rabbit');
```

That one line synchronizes your test with the application state. Playwright waits for the API to return before proceeding.

###### Fix 2: Wait for the API Response

If you do not know the exact data value to assert on, wait for the API response instead:

```typescript
await page.getByRole('button', { name: 'Edit' }).first().click();
await page.waitForResponse('**/api/pettypes/*');
await inputField.fill('rabbit');
```

Use locator assertions when you know the expected value. Use `waitForResponse` when you need to wait for an API call but do not care about the specific data.

##### Reason 2: Random API Delays Cause Timeouts

Your test fails with a timeout error, sometimes on step two, sometimes on step six. This usually means your application has API endpoints with unpredictable response times. The default test timeout is 30 seconds; one 20-second API call pushes your test past it.

###### How to Identify Slow APIs

Open the trace viewer networking tab and sort API calls by duration. If the same endpoint spikes in duration across different runs, that is the source of your flakiness.

###### Fix: Use test.slow() and Mock Unstable Endpoints

```typescript
test('my flaky test', async ({ page }) => {
  test.slow();
});
```

`test.slow()` multiplies your default timeout by three. It is a diagnostic tool, not a permanent solution. The actual fix is to mock the slow endpoint:

```typescript
await page.route('**/api/slow-endpoint', async (route) => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify(mockData),
  });
});
```

If the endpoint cannot be mocked, adjust the timeout for that specific test:

```typescript
test('test with slow API', async ({ page }) => {
  test.setTimeout(60000);
});
```

##### Reason 3: Fragile Locators

If you are still using XPath with absolute paths, that is one of the reasons your tests are flaky. The longer your selector, the more likely it is to break when the DOM changes:

```typescript
// Do not do this
await page.locator('//div[@class="main"]/div[2]/table/tbody/tr[1]/td[3]/button').click();
```

###### Fix: Use User-Facing Locators

```typescript
await page.getByRole('button', { name: 'Edit' }).first().click();
await page.getByRole('textbox', { name: 'Pet name' }).fill('rabbit');
await page.getByRole('button', { name: 'Update' }).click();
```

The shorter your locator, the more stable it will be. `getByRole()`, `getByText()`, `getByLabel()`, and `getByTitle()` target user-visible attributes, not internal structure.

| Approach | Locator | Stability |
| --- | --- | --- |
| XPath (absolute) | `//div[@class="main"]/div[2]/table/tbody/tr[1]/td[3]/button` | Fragile |
| CSS (multi-node) | `div.main > div:nth-child(2) > table > tbody > tr:first-child button` | Fragile |
| User-facing | `getByRole('button', { name: 'Edit' })` | Stable |

One nice side effect: user-facing locators push you toward better accessibility. If you cannot find an element using `getByRole()`, it might be because the element is missing proper ARIA attributes.

##### Final Thoughts

Most flaky Playwright tests come down to three things: race conditions with async operations, unpredictable API response times, and fragile locators. Use locator assertions to synchronize your test with the application state. Use `test.slow()` and mocking to handle slow APIs. Use user-facing locators instead of XPath and long CSS selectors.

If your tests are flaky, the problem is in the code, not in the framework.

### 12. Artem Bondar — Page Object Model

- Source: https://bondaracademy.com/blog/what-is-page-object-model-in-test-automation
- Retrieved: 2026-08-29
- Firecrawl status: complete

Page Object Model is a **design pattern** used in test automation to organize your source code. The goal is to improve maintainability and reusability of your tests. You take repetitive parts of your test code, put them into methods inside a class, and then call that method instead of writing the same steps over and over again. No magic.

There is **no single industry-standard** for implementing page objects. The general concept: every page of your web application gets its own class, and that class contains methods responsible for the operations you perform on that page.

##### Why Do You Need Page Objects?

Without page objects:

```typescript
// Test 1
await page.locator('#email').fill('user@test.com')
await page.locator('#password').fill('password123')
await page.locator('button:has-text("Login")').click()
// Test 2
await page.locator('#email').fill('user@test.com')
await page.locator('#password').fill('password123')
await page.locator('button:has-text("Login")').click()
```

Three lines repeated in every test. If the dev team renames the login button, you have to go through every test file.

You create a page object class that owns the login behavior:

```typescript
class LoginPage {
  readonly page: Page
  constructor(page: Page) {
    this.page = page
  }
  async performLogin(email: string, password: string) {
    await this.page.locator('#email').fill(email)
    await this.page.locator('#password').fill(password)
    await this.page.locator('button:has-text("Login")').click()
  }
}
```

Now your tests become clean:

```typescript
const loginPage = new LoginPage(page)
await loginPage.performLogin('user@test.com', 'password123')
```

If the button changes from "Login" to "Sign In," you update it in one place. Zero test file edits.

##### Two Principles Every Page Object Must Follow

###### DRY: Do not Repeat Yourself

If you are copy-pasting the same code more than three times, stop. Create a reusable method. If a login flow appears in 30 tests and the login form changes, would you rather update 30 files or one file?

###### KISS: Keep It Simple Stupid

This is the more important principle, and the one most people get wrong. It is very easy to overcomplicate framework design. Extra methods for every tiny interaction. Helper classes wrapping helper classes. Abstract base page classes with three levels of inheritance.

The real test of your framework: what happens when you hand it to a new engineer who just joined the team? If they can look at your page objects, understand how they work, and start writing tests on day one, you did a great job. If it is too complex or too clever, they will remove it and start from scratch.

##### Page Object Best Practices

###### Use Descriptive Naming

Avoid shortcuts, acronyms, abbreviations. Instead of `clickLogin()`, name it `clickLoginButton()`. Instead of `fillForm()`, name it `fillRegistrationForm()`. Instead of `nav()`, name it `navigateToHomePage()`.

If a colleague reads `loginPage.performLogin()` followed by `dashboardPage.createNewProject()` followed by `projectPage.verifyProjectTitle()`, they should understand the entire test flow without looking at implementation code.

###### Avoid Tiny Single-Line Methods

Methods like `clickLoginButton()` that contain just a single line of code: try to avoid them when you can. If every interaction on a page gets its own method, your class ends up with 50 tiny methods. Instead, group several meaningful test steps into methods that represent a functional operation on the page. A user does not "click the email field, type an email, click the password field, type a password, click the login button." A user **logs in**. That is one method: `performLogin()`. Think in user actions, not individual clicks.

##### Final Thoughts

Page Object Model keeps your tests clean and maintainable. Take repetitive code, put it into well-named methods inside page classes, and give your tests a structure that scales. Build your framework for the people who will use it. Follow DRY and KISS. Use descriptive names. Group meaningful operations instead of wrapping every click in its own method.

### 13. Artem Bondar — JSON schema API testing

- Source: https://bondaracademy.com/blog/json-schema-testing-playwright
- Retrieved: 2026-08-29
- Firecrawl status: complete

JSON Schema is a JSON object that describes the structure of another JSON object. Think of it as a contract. It defines what properties should be in the response, what types those properties should have, and the overall structure.

Say your API returns:

```json
{
  "firstName": "John",
  "lastName": "Smith",
  "age": 35
}
```

The JSON Schema for this response:

```json
{
  "type": "object",
  "properties": {
    "firstName": { "type": "string" },
    "lastName": { "type": "string" },
    "age": { "type": "number" }
  },
  "required": ["firstName", "lastName", "age"]
}
```

If the API suddenly removes `age` from the response, the schema validation fails. If `age` comes back as a string instead of a number, the validation fails.

##### Why Not Just Assert Every Property?

Real API responses are not that simple. A typical articles endpoint can have 200 lines of JSON with nested objects, arrays, and dozens of properties. JSON Schema handles this much more intelligently. A 200-line response might produce a schema of just 85 lines, because schemas understand repetitive structures: an array of 10 article objects defines that structure once.

##### How to Create a JSON Schema

You do not have to write schemas by hand. Use a JSON-to-JSON-Schema converter like transform.tools. Workflow: send a request to your API, copy the response body, paste it into a converter, review the generated schema, save it as a file in your test project (e.g., `schemas/tags.schema.json`).

##### Setting Up JSON Schema Validation in Playwright

Playwright does not have built-in JSON Schema validation, so you need a validation library. The most popular choice is Ajv (Another JSON Schema Validator):

```bash
npm install ajv --save-dev
```

Create a helper function you can reuse across all your tests:

```typescript
import Ajv from "ajv";
const ajv = new Ajv();
export function validateJsonSchema(data: object, schema: object) {
  const validate = ajv.compile(schema);
  const isValid = validate(data);
  return { isValid, errors: validate.errors };
}
```

##### Simple Example

The tags endpoint returns `{ "tags": ["coding", "testing", "playwright"] }`. The schema:

```json
{
  "type": "object",
  "properties": {
    "tags": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["tags"]
}
```

The test:

```typescript
import { test, expect } from "@playwright/test";
import { validateJsonSchema } from "../utils/validateJsonSchema";
import tagsSchema from "../schemas/tags.schema.json";

test("tags response matches JSON schema", async ({ request }) => {
  const response = await request.get("/api/tags");
  const body = await response.json();
  const { isValid, errors } = validateJsonSchema(body, tagsSchema);
  expect(isValid, `Schema errors: ${JSON.stringify(errors)}`).toBe(true);
});
```

One test catches: numbers instead of strings, an object instead of an array, a missing `tags` property, and a renamed property.

##### Complex Example

For an articles endpoint with 200+ lines of nested JSON, the test looks almost identical to the simple one. Whether your response has 3 properties or 300, the test code does not change.

##### Required vs Optional Properties

Not every property in your schema needs to be `required`. When a property is required and missing, validation fails. When it is not required and missing, validation passes. Define the contract based on what your API actually guarantees.

##### JSON Schema and Contract Testing

When you validate your API response against a JSON Schema, you are doing **provider-driven contract testing**. The API is your provider. The schema is your contract. If either side breaks the contract, tests catch it. This works especially well for teams where frontend and backend are developed separately.

##### Best Practices

Keep schema files in a dedicated `schemas/` folder. When the API changes intentionally, regenerate your schemas. Schema validation checks the structure; functional tests check values and logic. Use both. Pass Ajv error messages into your assertion message so they show up in the test report.

### 14. Artem Bondar — Fixtures

- Source: https://bondaracademy.com/blog/how-to-use-playwright-fixtures
- Retrieved: 2026-08-29
- Firecrawl status: complete

Think of **fixtures** as functions that run some code for you before a test or after a test. If you have used `beforeEach` and `afterEach` hooks, you already get the idea. Fixtures do the same thing, but with extra features.

First, fixtures only run when a test actually calls them (except auto-fixtures). Second, fixtures can pass values directly into your tests. Third, fixtures can depend on other fixtures, and you can scope them to run once per worker instead of once per test.

##### Creating Your First Playwright Fixture

The setup we all know:

```typescript
import { test } from '@playwright/test';
test.beforeEach(async () => {
  console.log('Hello World');
});
test('test one', async () => {
  console.log('Where is my candy?');
});
```

Create a new file called `fixture.ts`:

```typescript
import { test as base } from '@playwright/test';
type MyFixtures = {
  helloWorld: string;
};
export const test = base.extend<MyFixtures>({
  helloWorld: async ({}, use) => {
    console.log('Hello World');
    await use();
    console.log('Goodbye');
  },
});
```

Update your test file to import `test` from your fixture file instead of from `@playwright/test`:

```typescript
import { test } from './fixture';
test('test one', async ({ helloWorld }) => {
  console.log('Where is my candy?');
});
```

##### Fixture Execution Order: Before and After Use

The console output:

```
Hello World
Where is my candy?
Goodbye
```

Everything before `await use()` runs **before** the test. Everything after `await use()` runs **after** the test. One fixture replaces both `beforeEach` and `afterEach`. The `use` callback is where Playwright hands control to your test. Setup and teardown live in a single function.

##### How to Pass Values from Fixtures to Tests

Whatever you pass into the `use` callback becomes available inside your test:

```typescript
helloWorld: async ({}, use) => {
  const myWorld = 'Hello World';
  await use(myWorld);
},
```

```typescript
test('test one', async ({ helloWorld }) => {
  console.log(helloWorld);
  console.log('Where is my candy?');
});
```

We drive execution not by the order in the fixture. The fixture still returns the value, but we call it later in the test.

##### Fixture Dependencies in Playwright

One fixture can call another fixture:

```typescript
type MyFixtures = {
  helloWorld: string;
  greatDay: string;
};
export const test = base.extend<MyFixtures>({
  helloWorld: async ({}, use) => {
    const myWorld = 'Hello World';
    await use(myWorld);
    console.log('Goodbye');
  },
  greatDay: async ({ helloWorld }, use) => {
    const myDay = helloWorld + ', what a great day';
    await use(myDay);
  },
});
```

The teardown order is reversed: first the `greatDay` cleanup runs, then `helloWorld` prints "Goodbye". That is how cascading teardown works.

You can also pass built-in Playwright fixtures like `page` and `request` into your custom fixtures:

```typescript
myFixture: async ({ page, request }, use) => {
  await page.goto('https://example.com');
  await use(page);
},
```

##### Worker-Scoped Fixtures for Parallel Testing

A worker is a single executor of your tests. Worker-scoped fixtures run once when a worker starts and stay active for every test that worker executes:

```typescript
type WorkerFixture = {
  cupOfCoffee: string;
};
export const test = base.extend<MyFixtures, WorkerFixture>({
  cupOfCoffee: [async ({}, use, workerInfo) => {
    const cup = 'Cup of coffee number ' + workerInfo.workerIndex;
    await use(cup);
  }, { scope: 'worker' }],
});
```

Using the worker index, you can pull a test account by its index, avoiding concurrency issues. Or create an access token only once per worker: if the test fails, Playwright recreates a new worker, which triggers a new token creation.

##### Automatic Fixtures

**Automatic fixtures** use `{ auto: true }` instead of `{ scope: 'worker' }` and run for every test, even if you did not call them in your test.

##### Do not Overuse Playwright Fixtures

Do not use fixtures as page objects. Use fixtures for high-level test setup: authentication, test data creation, environment configuration, and API setup. When you create too many fixtures, like 20 or 30, it becomes hard to manage. For locator strategies and page interactions, classes and functions remain the right tools.

##### Final Thoughts

Fixtures are set up and teardown functions with extra power. On-demand execution, value passing, dependency chaining, and worker scoping. Start with a simple fixture that replaces a `beforeEach`, and add complexity only when your tests need it.

### 15. Artem Bondar — Copy as Prompt

- Source: https://bondaracademy.com/blog/playwright-copy-as-prompt
- Retrieved: 2026-08-29
- Firecrawl status: complete

Starting with version 1.51, Playwright introduced a feature called **Copy as Prompt**. It extracts the full context of a test failure and lets you paste it into any LLM, like Claude or ChatGPT, to get a clear explanation of what happened.

##### What Is Playwright Copy as Prompt?

Copy as Prompt is a button in the Playwright HTML Reporter. When a test fails, you open the report, click the button, and it copies a structured prompt to your clipboard. No plugins, no configuration. It ships with Playwright out of the box starting from version 1.51.

The prompt has four parts:

1. AI instructions — a system-level message telling the AI to explain the failure, be concise, respect Playwright best practices, and provide code fix snippets if possible.
2. Test info — the test name, file path, and configuration details.
3. Error details — the full error message, including the assertion output with expected vs. received values.
4. Source code — the actual test code from your spec file.

##### Example 1: Simple Assertion Mismatch

A test selects an owner by phone number and validates that the phone number is displayed on the owner information page:

```typescript
test('select owner by phone number', async ({ page }) => {
  await page.goto('/owners');
  await page.getByRole('row', { name: '6085552765' }).getByRole('link').click();
  await expect(page.locator('.ownerInfo')).toContainText('6085552768');
});
```

Pasting the prompt into Claude returns: "The test selects the owner with phone number `6085552765`, but the assertion expects `6085552768`. The expected number does not match the owner phone number." The assertion value is simply wrong — a typo.

##### Example 2: Complex Web Table Parsing Error

A test validates that the correct pets are listed for owners in Madison city. It loops through table rows, extracts cell values, and compares them to an expected array:

```typescript
test('validate pets of Madison city', async ({ page }) => {
  await page.goto('/owners');
  const rows = page.getByRole('row').filter({ hasText: 'Madison' });
  const petNames: string[] = [];
  for (let i = 0; i < await rows.count(); i++) {
    const cell = rows.nth(i).getByRole('cell').nth(2);
    const text = (await cell.innerText()).trim();
    petNames.push(text);
  }
  expect(petNames).toEqual(['Leo', 'George', 'Mulligan']);
});
```

The AI explanation: "The test is failing because the pet name cell contains additional text. Instead of just Leo, the cell contains Leo followed by a newline and extra text. The `trim()` method only removes leading and trailing whitespace, not internal newlines."

The fix: split the text by newline and take only the first value:

```typescript
const text = (await cell.innerText()).split('\n')[0].trim();
petNames.push(text);
```

##### AI Explanation vs. AI Fix: Know the Difference

The explanation is almost always accurate. The suggested fix is not always the best approach. The AI gets the "why" right about 99% of the time. But the code fix it suggests sometimes does not follow Playwright best practices or fit your specific test scenario. Use the AI to understand the failure. Then decide how to fix it yourself based on your application context.

##### Where to Find the Copy as Prompt Button

Three places: the **HTML Reporter** (`npx playwright show-report`), the **Trace Viewer**, and **UI Mode** (`npx playwright test --ui`). All three give you the same structured prompt.

##### When Copy as Prompt Will Not Help

If your test fails due to flaky infrastructure, timing issues, or environment-specific problems, the AI will not know that. It only sees the error message and code. For flaky tests, you still need to investigate the environment. But for assertion mismatches, wrong locators, and logic errors in your test code? This is where Copy as Prompt really shines.

##### Final Thoughts

Click a button, paste into an AI, and get an explanation in plain English. Use it to understand why the test fails. Make the fix yourself. That is the winning formula.

What if you could take your existing Playwright UI test and convert it into a pure API test with the help of AI? Just record, clean, prompt, and let AI generate the test for you.

##### Why convert UI tests to API tests?

UI tests are slow. They depend on the browser. They break when someone changes a button label. API tests? Fast, stable, and focused on business logic. If your UI test is just creating data, validating it exists, and deleting it, you do not need a browser for that.

##### The workflow: UI test to API test in 4 steps

1. **Record** the network activity of your UI test using Playwright HAR recording
2. **Clean** the HAR file to keep only the relevant API calls
3. **Prepare** instructions and a prompt for the AI agent
4. **Generate** the API test by feeding everything into an AI coding assistant

##### Step 1: Record network activity with Playwright HAR

```typescript
const context = await browser.newContext({
  recordHar: {
    path: 'output.har',
    mode: 'minimal'
  }
});
```

The `mode: 'minimal'` setting is important. Without it, the file gets huge. After running the UI test with HAR recording enabled, Playwright generates an `output.har` file that was almost **3,000 lines long**, including JavaScript bundles, images, and static resources.

##### Step 2: Clean and filter the HAR file

A raw HAR file is too noisy for AI to work with. Clean input produces clean output. A Node.js script filters by URL to keep only requests to the API endpoints, removes headers, cookies, and body size, strips out static resources, and keeps only what matters: the request method, URL, request body, and response data.

The result: a `filtered-har.json` file with only **400 lines** instead of 3,000.

##### Step 3: Prepare AI instructions and prompt

Dumping a HAR file into the AI agent and saying "Make me an API test" produces garbage. AI needs context.

Three documents:

**Framework description (`copilot-instructions.md`)** — how the custom API testing framework works: technologies, project structure, design patterns (custom methods like `path()`, `params()`, `getRequest()`), schema validation approach (`shouldMatchSchema()`), and authentication handling.

**HAR processing instructions (`har-processing.instructions.md`)** — teaches the AI how to read the HAR JSON structure: where to find the request method, URL, request body; how to extract path segments and query parameters; how to create variables from response data; how to use the faker library for dynamic test data. Include concrete examples like chaining an article slug from a POST response into a subsequent GET:

```typescript
// Example: Create article, then get it by slug
const createResponse = await api
  .path('/articles')
  .body(articleData)
  .postRequest(201)

const articleSlug = createResponse.article.slug

const getResponse = await api
  .path(`/articles/${articleSlug}`)
  .getRequest(200)
```

**The prompt** — surprisingly short: "Process the provided HAR file and create a single comprehensive API test." Invest your time in writing good instructions. The instructions are reusable across every test you generate. The prompt is just the trigger.

##### Step 4: Generate the API test with AI

Add the cleaned HAR file, the processing instructions, and the generation prompt to the AI context. The agent analyzed the HAR file, looked at the existing code for reference, and produced a complete API test that followed the framework patterns, used the faker library, correctly chained responses, and matched the custom method syntax.

##### Tips for better AI-generated API tests

- **Instructions matter more than prompts.** Spend 80% of your effort on the instruction file.
- **Clean your input data.** 400 focused lines beat 3,000 noisy ones every time.
- **Show variable chaining with examples.** Without them, the AI will hardcode values or miss the connection between requests.
- **Always review the output.** AI gives you a head start, not a finished product. Also make sure your instructions tell the AI to include schema validation.

### 17. Artem Bondar — getByRole

- Source: https://bondaracademy.com/blog/how-to-use-getbyrole-in-playwright
- Retrieved: 2026-08-29
- Firecrawl status: complete

If you are transitioning from Cypress or Selenium to Playwright, you have probably noticed something unfamiliar: `getByRole()`. The Playwright documentation says: "To make tests resilient, we recommend prioritizing user-visible attributes and explicit contracts such as `getByRole()`." In other words, this is the **recommended way** to locate web elements in Playwright.

##### What is getByRole() in Playwright?

The "role" refers to [ARIA roles](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Roles) — attributes that assistive technologies use to read and navigate web applications. Playwright taps into this same accessibility layer. When you use `getByRole()`, you are locating elements the way a real user would.

```typescript
page.getByRole('role', { name: 'visible text' })
```

You provide the **role** of the element (button, link, textbox, etc.) and the **name**, which is usually the visible text label. Together, these two pieces create a locator that is both unique and easy to read.

##### The Only Roles You Actually Need

| Role | HTML Element | Use Case |
| --- | --- | --- |
| `button` | `<button>`, `<input type="submit">` | Click buttons, submit forms |
| `textbox` | `<input>`, `<textarea>` | Fill input fields |
| `link` | `<a>` | Click hyperlinks and navigation items |
| `checkbox` | `<input type="checkbox">` | Check or uncheck checkboxes |
| `radio` | `<input type="radio">` | Select radio buttons |
| `heading` | `<h1>` to `<h6>` | Assert page headers |
| `row` | `<tr>` | Target rows in web tables |
| `cell` | `<td>` | Target cells in web tables |
| `listitem` | `<li>` | Interact with list items |

Nine roles that cover the vast majority of your test automation needs.

##### How to Make getByRole() Unique with the Name Option

A role by itself is not unique. The key is the **name** option:

```typescript
// Role alone - too broad, matches every button
page.getByRole('button')
// Role + name — specific and readable
page.getByRole('button', { name: 'Send' })
```

The accessible name typically maps to the text content of buttons and links, the label or placeholder of input fields, and the text of checkboxes and radio buttons.

##### Practical getByRole() Examples in Playwright

Clicking a link:

```typescript
await page.getByRole('link', { name: 'Forms' }).click();
```

Checking a checkbox — use `.check()` instead of `.click()`, because `.check()` will not uncheck the box if it is already checked:

```typescript
await page.getByRole('checkbox', { name: 'Check me out' }).check();
```

Filling an input field:

```typescript
await page.getByRole('textbox', { name: 'Recipients' }).fill('John Smith');
```

Clicking a button:

```typescript
await page.getByRole('button', { name: 'Send' }).click();
```

Asserting a heading, with optional level filter:

```typescript
await expect(page.getByRole('heading', { name: 'Form Layouts' })).toBeVisible();
await expect(page.getByRole('heading', { name: 'Form Layouts', level: 1 })).toBeVisible();
```

##### How to Chain getByRole() with Other Locators

You can chain `getByRole()` with regular locators. Find a form by its ID first, then locate an input field inside it:

```typescript
await page.locator('#contactForm').getByRole('textbox', { name: 'Email' }).fill('test@example.com');
```

Or the other way around:

```typescript
const row = page.getByRole('row', { name: 'John Smith' });
await row.locator('td').first().click();
```

##### When NOT to Use getByRole()

**Icons without text** — `getByRole()` will not help; use a CSS selector or test ID.

**Dynamic dropdowns** — a locator tied to the current test data breaks when the value changes. Use a CSS selector that targets the dropdown by its structure.

**Non-unique text** — if the same button text appears multiple times, chain it with a parent locator or use a different locator strategy.

The rule of thumb: if the element has **static, visible text** that uniquely identifies it, use `getByRole()`. Otherwise, reach for regular locators.

##### getByRole() vs Other Playwright Locators

| Locator | Best For | Example |
| --- | --- | --- |
| `getByRole()` | Interactive elements with visible text | `getByRole('button', { name: 'Submit' })` |
| `getByText()` | Static text content, paragraphs, labels | `getByText('Welcome back')` |
| `getByLabel()` | Form inputs by their `<label>` | `getByLabel('Email address')` |
| `getByPlaceholder()` | Inputs by placeholder text | `getByPlaceholder('Search...')` |
| `getByTestId()` | Elements with `data-testid` attribute | `getByTestId('submit-btn')` |
| `locator()` | CSS when nothing else works | `locator('#sidebar .nav-item')` |

##### Best Practices

1. **Always provide the name option.** A role without a name matches too many things.
2. **Use proper HTML in your application.** `getByRole()` works best with semantic HTML — `<button>` instead of `<div onclick>`.
3. **Prefer role-specific methods over `.click()`.** Use `.check()` for checkboxes, `.fill()` for textboxes, `.selectOption()` for dropdowns.
4. **Use the `exact` option for precise matching:** `page.getByRole('button', { name: 'Send', exact: true })`.

Playwright is the No. 1 framework for UI test automation. But it also has API testing capabilities. Using a single framework, you can test both the UI and the API for your web application.

There are 4 pre-defined Playwright fixtures: Page, Request, Context, Browser. We are interested in two of those:

- **GET**: Read the record from the API resource
- **PUT**: Update the existing record

test('Create Article', async ({ request }) => {

##### API Testing Framework

Playwright was not optimized for API testing. The API capabilities primarily complement functional UI automation — for example, faster creation of preconditions for UI test execution. If you want to use Playwright for API testing, build a custom framework around it.

The same test written in pure Playwright versus the **Fluent Interface Design** pattern:

```typescript
test('Create and Delete Article', async ({ api }) => {
    const createArticleResponse = await api
        .path('/articles')
        .body({ "article": { "title": "Test TWO TEST", "description": "Test description", "body": "Test body", "tagList": [] } })
        .postRequest(201)

    await expect(createArticleResponse).shouldMatchSchema('articles', 'POST_articles')
    expect(createArticleResponse.article.title).shouldEqual('Test TWO TEST')

    const slugId = createArticleResponse.article.slug

    const articlesResponse = await api
        .path('/articles')
        .params({ limit: 10, offset: 0 })
        .getRequest(200)

    expect(articlesResponse.articles[0].title).shouldEqual('Test TWO TEST')

    await api
        .path(`/articles/${slugId}`)
        .deleteRequest(204)
})
```

The framework provides chainable methods:

- **path()** — the path of the API resource to call
- **params()** — URL query parameters
- **body()** — a JSON request object for PUT or POST
- **getRequest()** / **postRequest()** / **putRequest()** / **deleteRequest()** — make the request and automatically validate the status code

This separation of responsibilities makes scripting easier, with fewer lines of code and easier maintenance.

### 19. Artem Bondar — Not waiting for elements

- Source: https://bondaracademy.com/blog/playwright-not-waiting-for-elements
- Retrieved: 2026-08-29
- Firecrawl status: complete

Playwright is a powerful test automation framework. Its ability to automatically wait for elements before interacting with them is a standout feature. However, this auto-waiting mechanism does not always work perfectly. Sometimes Playwright tries to interact with elements before they are ready. Other times, it returns incomplete lists of elements.

##### How Auto-Waiting Really Works

1. **Locators are just instructions.** When you create a locator in Playwright, it is not actively searching for anything yet. It is a set of instructions for later use.

2. **Actions trigger the search.** Playwright only starts looking for web elements when you perform an "action" on a locator, like `click()` or `fill()`.

3. **Each action has its own checklist.** Different actions have different sets of "actionability checks" they perform before executing:

- **Visible:** Is the element actually visible on the page?
- **Stable:** Has the element stopped moving around?
- **Receives Events:** Can the element respond to user interactions?
- **Enabled:** Is the element not disabled?
- **Editable:** For input elements, can we actually type into them?

`click()` needs Visible, Stable, Receives Events, and Enabled, while `selectText()` only cares if the element is visible.

##### When Auto-Waiting Fails

Not all Playwright methods trigger this mechanism. Two common ones are `all()` and `allTextContents()`. These methods execute immediately when called, without waiting for any actionability checks. If your page is not fully loaded when these methods run, you might get empty or partial results.

##### Manual Dynamic Waiting

Playwright offers a toolkit of dynamic waiting methods:

- `await page.waitForEvent()`: perfect for waiting on specific page events.
- `await page.waitForFunction()`: ideal for custom waiting conditions.
- `await page.waitForLoadState()`: ensures the page has reached a certain load state, such as "networkidle".
- `await page.waitForRequest()`: waits for a specific network request to be initiated.
- `await page.waitForResponse()`: waits for a specific network response to be received.
- `await page.waitForSelector()`: waits for a specific element to appear in the DOM.
- `await page.waitForURL()`: waits for the page URL to match a certain pattern.
- `waitFor()`: chained as an "action" command for a specific locator to be ready.

All these methods are dynamic wait forms. Playwright will wait for the expected condition for up to the timeout.

##### Handling Web Table Rows

Tables may load asynchronously. Two common scenarios:

For tables that load all rows at once:

```typescript
await page.waitForSelector('table')
const rows = await page.locator('table tr').all();
```

For tables with dynamically loaded data:

```typescript
await page.waitForResponse(response => response.url().includes('/api/tableData'))
const rows = await page.locator('table tr').all();
```

Waiting for the API response ensures the data is loaded before you attempt to access it.

##### Dealing with Lists of Text Values

The `allTextContents()` method can return incomplete results if the list is not fully loaded. Three strategies:

Use locator assertions:

```typescript
await expect(page.locator('.list-item')).toHaveText(/Expected Text/)
const textList = await page.locator('.list-item').allTextContents();
```

Wait for the API that populates the list:

```typescript
await page.waitForResponse(response => response.url().includes('/api/listData'))
const textList = await page.locator('.list-item').allTextContents();
```

Wait for a stable parent element:

```typescript
await page.waitForSelector('ul.list-container')
const textList = await page.locator('.list-item').allTextContents();
```

##### The Key to Reliable Playwright Tests

When you use Playwright action commands that do not have an auto-waiting mechanism, you need to handle the waiting yourself. Use one of the dynamic wait methods before the step with the action command. That ensures the application is loaded into the correct state when the action executes.

Locators are the cornerstone of element interaction in Playwright. They are **identifiers** that allow your tests to find and manipulate specific elements on a web page. Choosing the right locator strategy is critical for test stability and maintenance.

There are two key approaches: user-facing attributes and CSS attributes.

##### User-Facing Attributes (Recommended)

Playwright strongly recommends prioritizing user-facing locators. These locators reflect how users and assistive technologies perceive the page.

###### 1. getByRole()

Your go-to method whenever possible. It selects elements based on their ARIA role, label, or other accessibility attributes:

```typescript
page.getByRole('button', { name: 'Submit' })
```

###### 2. getByLabel()

Ideal for form controls associated with a label:

```typescript
page.getByLabel('Email address')
```

###### 3. getByPlaceholder()

Selects input elements based on their placeholder text:

```typescript
page.getByPlaceholder('Enter your username')
```

###### 4. getByText()

Finds elements containing specific text content. A good approach if the text you are targeting is unique and static. Visible text inside input fields is a value, not text, so it cannot be selected by this method.

```typescript
page.getByText('Welcome to our site')
```

###### 5. getByAltText()

Locates images by their alt text:

```typescript
page.getByAltText('Company logo')
```

###### 6. getByTitle()

Selects elements with a matching "title" attribute:

```typescript
page.getByTitle('More information')
```

##### CSS Attributes

Use the `locator()` method with CSS selectors.

Find by ID:

```typescript
page.locator('#myIdValue')
```

Find by class:

```typescript
page.locator('.myClassValue')
page.locator('.myClassValue1.myClassValue2')
```

Find by HTML tag:

```typescript
page.locator('button')
page.locator('button.primary')
```

Find by attribute:

```typescript
page.locator('[value]')
page.locator('[value="green"]')
```

Avoid XPath selectors in Playwright. They are considered a bad practice due to their brittleness and poor performance.

##### Using Filters

Make the locator more unique by providing a second argument, or use a `filter()` method with identical behavior:

```typescript
page.locator('button', {hasText: "Log In"})
page.locator('button').filter({hasText: "Log In"})
```

The `filter()` method can also be applied to user-facing locators:

```typescript
page.getByRole('link').filter({ hasText: 'Learn more' })
```

Prioritize the second argument over the `filter()` method when possible for concise code. Use a `filter()` method for multi-level filtration.

##### Chaining Locators

Combine multiple locators to create more specific selectors:

```typescript
page.locator('app-form').getByRole('button', { name: 'Submit' })
```

##### The Locator Picker: Your Secret Weapon

Access it through the Playwright VS Code extension (click "Pick locator" at the bottom of the test explorer) or through Playwright UI Mode (`npx playwright test --ui`, then select "Pick locator"). This tool is a massive time-saver and helps ensure you are following best practices.

##### Best Practices for Playwright Locators

1. Prioritize user-facing attributes (getByRole, getByLabel, etc.) whenever possible.
2. Use CSS selectors as a fallback when user-facing attributes are not suitable.
3. Avoid XPath selectors entirely.
4. Leverage the Locator Picker to quickly generate optimal locators.
5. Chain locators for increased specificity when needed.
6. Use filters to further refine your element selection.
7. Keep locators as simple and readable as possible.
8. When using `getByRole()`, include the accessible name for precision.
9. Regularly review and update your locators as the application evolves.
10. Document your locator strategy for your team.

Remember, the key is to think like a user, not a machine. Choose locators that reflect how people interact with your application, and your tests will be more resilient and meaningful.

### 21. Artem Bondar — Timeout 30000ms

- Source: https://bondaracademy.com/blog/playwright-timeout-30000ms-exceeded
- Retrieved: 2026-08-29
- Firecrawl status: complete

Before we tackle the error, it is crucial to understand the different types of timeouts in Playwright. This knowledge forms the foundation for effectively diagnosing and resolving timeout issues.

###### Global Timeout

The global timeout sets the maximum time limit for the entire test run. It applies to all tests in your suite collectively. If you set a global timeout of 5 minutes for a suite of 10 tests, the entire execution will stop if it exceeds this 5-minute limit, regardless of how many tests have completed.

###### Test Timeout

This is the timeout we are dealing with in the "30000ms exceeded" error. By default, Playwright sets a 30-second timeout for each test. If a single test execution time surpasses this limit, Playwright halts the test and throws an error.

###### Action Timeout

Action timeouts apply to specific Playwright commands, such as `click()`, `fill()`, `check()`. Playwright does not set a default action timeout; it uses the test timeout as the upper limit for these actions.

###### Navigation Timeout

This timeout governs the maximum time allowed for page navigation events. Navigation timeouts are not configured by default and defer to the test timeout. This can be problematic on slow-loading pages, as a single navigation event may consume the entire test timeout.

###### Expect Timeout

Expect timeouts are specific to Locator Assertions in your tests. By default, Playwright sets this to 5 seconds. This shorter assertion timeout helps identify issues more quickly than waiting for the full test timeout.

##### Common Causes of Timeout Errors

###### 1. Slow Test Execution

Your test might simply be too slow to complete within 30 seconds. This is particularly common in CI/CD environments. If you run your test several times and it fails **at a different point** with a "timeout 30000ms exceeded" error on every re-run, it means that 30 seconds was not enough to complete it.

###### 2. Incorrect Locators

If Playwright cannot find an element using the provided locator, it will continue searching until the test timeout is reached. If you run your test several times and it fails **at the same point** on every re-run, most likely the problem is with the locator. Examine the error message — a grayed-out text tells you where to look.

###### 3. Slow Backend Responses

If your application backend is slow to respond, your tests may timeout. Playwright may timeout while waiting for the application to reach a testable state.

##### Strategies to Resolve Timeout Errors

###### 1. Adjusting Timeout Duration

At the framework level:

```typescript
import { defineConfig } from '@playwright/test';
export default defineConfig({
  timeout: 60000,
});
```

At the hook level or for individual tests:

```typescript
import {test} from '@playwright/test';
test.beforeEach( async ({ page }) => {
    test.setTimeout(40000)
    await page.goto('/')
})
test('hello', async ({ page }) => {
    //this test can run up to 40 seconds
});
test('world', async ({ page }) => {
    test.setTimeout(60000)
});
```

###### 2. Optimizing Locators

Ensure your locators are accurate and efficient. Use user-facing locators instead of IDs, CSS, or other less reliable selectors:

```typescript
// Instead of:
await page.locator('button.submit-form').click();
// Use:
await page.getByRole('button', {name: "Submit"}).click();
```

###### 3. Mocking Slow Endpoints

```typescript
await page.route('**/api/slow-endpoint', route => {
  route.fulfill({
    status: 200,
    body: JSON.stringify({ data: 'mocked response' })
  });
});
```

##### Best Practices for Handling Timeouts

- Use specific timeouts: set specific timeouts for actions and navigations when necessary.
- Configure the framework to have a separate timeout for CI/CD execution and the local environment.
- Do not set a too-long default timeout in the framework configuration. For slow end-to-end tests, configure a timeout at the test level.
- Use Locator Assertions instead of Generic Assertions for anything web-related. Locator assertions have their own timeout.

##### Conclusion

The "timeout 30000ms exceeded" error is often a symptom of underlying issues in your tests or application. Increasing timeouts is often a band-aid solution. The goal should be to optimize your tests and application to perform within reasonable time frames.

### 22. Artem Bondar — Expect assertions

- Source: https://bondaracademy.com/blog/how-to-use-playwright-expect-assertions
- Retrieved: 2026-08-29
- Firecrawl status: complete

Playwright has two types of assertions: **Locator Assertions** and **Generic Assertions**. Both start with the `expect()` method, but they are entirely different beasts.

##### Generic Assertions: The Quick and Dirty

- Execute immediately
- Give you instant results
- Do not know anything about your app
- Take two arguments and run with them

```typescript
const result = 2 + 2
expect(result).toBe(4);
```

##### Locator Assertions: The Smart Cookie

- Only work with web element locators
- Perform checks against that locator
- Retry if things do not work out at first
- Have a 5-second timeout limit (but you can change that)

```typescript
await expect(page.locator('#submit-button')).toBeVisible();
```

##### The Assertion Selection: Which is which?

Generic Assertions: do not use `await`; the argument must be a value.

Locator Assertions: must use `await`; provide a locator as the argument.

Hover over the assertion method in VS Code. It will tell you what you are dealing with.

##### Best Practices

Locator assertions are your go-to. Use them for anything web-related. Save generic assertions for simple data comparisons. Locator assertions have a built-in wait mechanism; they make your tests more stable and less flaky.

| Generic Assertions | Locator Assertions |
| --- | --- |
| Immediate execution | Retry mechanism |
| Any data type | Web elements only |
| No built-in wait | 5-second default timeout |

##### Common Pitfalls

Checking text in an input field — instead of:

```typescript
const inputValue = await page.inputValue('#myInput');
expect(inputValue).toBe('Expected Text');
```

Do this:

```typescript
await expect(page.locator('#myInput')).toHaveValue('Expected Text');
```

**Here is the crucial difference:** with Generic Assertion, `inputValue()` waits until a value is available (up to the test timeout), grabs it, assigns it to a constant, and Playwright immediately checks whether it matches. With Locator Assertion, Playwright waits up to 5 seconds for the "Expected Text" to appear in the input field. If there is any other value currently, it keeps checking until the expected value shows up or the timeout is reached.

Checking the number of items in a list:

```typescript
// The old way:
const itemCount = await page.locator('.list-item').count();
expect(itemCount).toBe(5);
// The Playwright way:
await expect(page.locator('.list-item')).toHaveCount(5);
```

Checking for an empty input:

```typescript
// Instead of:
const inputValue = await page.inputValue('#myInput');
expect(inputValue).toBe('');
// Do this:
await expect(page.locator('#myInput')).toBeEmpty();
```

##### Timing is Everything: Configuring Timeouts

Globally in playwright.config.ts:

```typescript
export default defineConfig({
  expect: {
    timeout: 10000
  }
});
```

For individual assertions:

```typescript
await expect(page.locator('#slow-element')).toBeVisible({ timeout: 30000 });
```

These timeouts are not hard waits. They are more like "up to" times. If the element shows up sooner, you are golden.

##### Troubleshooting

If you are not seeing the assertion methods you expect: for locator assertions, make sure you have `await` and you are using a locator. For generic assertions, skip the `await` and use a plain value. When using generic assertions, know the difference between `toBe()` and `toEqual()` — they are not always interchangeable.

### 23. Artem Bondar — toBe vs toEqual

- Source: https://bondaracademy.com/blog/tobe-vs-toequal-assertion-playwright
- Retrieved: 2026-08-29
- Firecrawl status: complete

The difference between **toBe()** and **toEqual()** assertions is not very intuitive. From the Playwright documentation:

**toBe()** — Compares value with `expected` by calling `Object.is`. This method compares objects by reference instead of their contents, similarly to the strict equality operator `===`.

**toEqual()** — Compares contents of the value with contents of `expected`, performing a "deep equality" check. For objects, this method recursively checks equality of all fields, rather than comparing objects by reference. For primitive values, this method is equivalent to `expect(value).toBe()`.

##### Assertion of primitives

In JavaScript, primitive values are: number, string, bigint, boolean, undefined, symbol, and null.

```typescript
test('assert primitive', () => {
  const sizeA = 5
  const sizeB = 5
  expect(sizeA).toEqual(sizeB)
  expect(sizeA).toBe(sizeB)
})
```

The test passes. When you assert primitives, it does not matter which assertion to use.

##### Assertion of objects

Two constants assigned the same-looking objects:

```typescript
test('assert objects', () => {
  const houseA = {size: 5}
  const houseB = {size: 5}
  expect(houseA).toEqual(houseB)
  expect(houseA).toBe(houseB)
})
```

**toEqual()** passes because it performs deep equality of the object content. **toBe()** fails because it does not look at the content; it looks at the reference to the object. `houseA` refers to one object, `houseB` refers to another object.

And to make it even clearer:

```typescript
test('assert objects', () => {
  const houseA = {size: 5}
  const houseB = houseA
  expect(houseA).toEqual(houseB)
  expect(houseA).toBe(houseB)
})
```

Here `houseB` refers to `houseA`, so both refer to the same object, and both assertions pass.

##### Summary

In most cases, `toEqual()` is all you need to assert deep data equality. But if you need to validate that not just the content but the reference to the object is the same, use `toBe()`. For primitive data types, it does not matter which assertion you use. Playwright best practice is to use Locator Assertions instead of `toBe()` or `toEqual()`, which are Generic Assertions.

### 24. Artem Bondar — Do not force

- Source: https://bondaracademy.com/blog/do-not-force-playwright
- Retrieved: 2026-08-29
- Firecrawl status: complete

Using `{force: true}` often can be a quick solution for non-clickable web elements in Playwright or Cypress. At first, it may seem like a great solution, but a major danger lies behind it.

##### The power of the {force: true}

Both the Cypress and Playwright frameworks have a fantastic auto-waiting mechanism. When you interact with web elements, the framework automatically runs many validation checks before the action: whether the element is visible, stable, can receive events, among others. If at least one of the actionability checks does not pass, the action is not performed at all, and the test fails.

Web applications are not perfect; they are flaky by design. Sometimes it does not make sense why the button is not clickable, as you can see it on the page. However, the framework does not have eyes; it can only read the code. And if the code says the element is not ready for the click event, it will patiently wait for this condition to be satisfied until the timeout expires.

When you pass the `{force:true}` flag into the action command, you are essentially telling the framework: "I know that you do not like something about this button, but I see it on the screen, so please do the same." The framework reply: "All right, I will click this button, but I am not responsible for the result anymore. Will it actually be clicked or not — it is now your problem, not mine."

##### Test flakiness

Disabling the actionability check by using `{force: true}` may fix the problem — your script is working. At the same time, you remove the "stability fuse" from your script. The framework is no longer helping you; it is just doing what you tell it to do. Removing the actionability checks inevitably results in more flaky tests. The more force you use, the flakier the tests become.

What is the solution? Write the test script without using force:

- Analyze the test script and the log output. It often gives you a clue about what is happening.
- Understand your application. Talk to developers and ask questions about observed behavior. They can provide suggestions or make a fix (it can be a bug).
- Look for a workaround to avoid using force as best as you can.

##### Giving the "force" back

A page object method was trying to select a checkbox, and since there was an issue in the application itself, the `{force: true}` flag was used to overcome this. The test sometimes works, sometimes not. The very first step to fix the flakiness was to remove `{force:true}` and check the log.

The log showed that the first two attempts to click the checkbox were intercepted by an element with the id "fixedban" — advertising banners interfered with the attempt. On the third attempt, the checkbox label intercepted the pointer event. This label is a sibling element in relation to the `<input>` element of the checkbox.

The idea: click on the parent `<div>` for those `<label>` and `<input>` elements. Since the `<div>` is a parent element in relation to `<label>`, the `<label>` element will not be able to intercept the pointer event.

Since Playwright best practice is to use user-visible locators, the code was refactored into just a single line:

```typescript
async hobbies_check(hobby: string) {
    await this.page.getByRole('checkbox', {name: hobby}).locator('..').click()
}
```

Now Playwright is responsible for waiting for this element to reach an actionable state and ensuring the click is performed only when the element is ready. This change made the test significantly more stable.

##### Final Thoughts

There are situations when, no matter what you try, you cannot perform an action on a desired web element. In such cases, the `{force:true}` flag can be a possible solution. But before doing that, make sure that you **really** tried everything. Also, run your tests multiple times in different environments, making sure that this particular step with a "force" flag is not flaky. And when your test fails, revisit the places where you have used force, making sure it is not the root cause.

### 26. Vitaliy Potapov — How Fixtures Work

- Source: https://vitalets.github.io/posts/playwright-in-pictures/how-fixtures-work/
- Retrieved: 2026-08-29
- Firecrawl status: complete

_**Playwright in Pictures** is a series of articles where the author uses [playwright-timeline-reporter](https://github.com/vitalets/playwright-timeline-reporter) to visualize different Playwright concepts with simple timeline charts._

[Fixtures](https://playwright.dev/docs/test-fixtures) are a central part of the Playwright runner. They let you move setup and teardown code out of the test body, so the test itself stays focused on the behavior you want to check. You can think of fixtures as before/after hooks on steroids.

But fixtures also make test execution less explicit. Fixture code can run before a test, after a test, once per worker, or even without being named in the test. This post goes through the main fixture patterns and shows what each one looks like on a timeline.

##### Simple Fixture

Fixtures are declared with `test.extend()`. Here is an example of the fixture `myTestFixture`:

```typescript
import { test as base } from '@playwright/test';

export const test = base.extend<{ myTestFixture: string }>({
  myTestFixture: async ({}, use) => {
    // fixture setup...
    await use('fixture value');
    // fixture teardown...
  },
});
```

Fixtures are test-scoped by default. A test-scoped fixture runs for every test that uses it. Because `myTestFixture` is test-scoped, Playwright creates a new instance for each test. The first instance is destroyed before the second one is created.

##### Fixtures Are Lazy

A fixture does not run just because it is declared. Playwright sets it up only when a test or another fixture asks for it. If a test does not reference the fixture, Playwright does not set it up for that test.

##### Auto Fixtures

Sometimes a fixture should run for every test. You do not need to add it to every test signature. Mark it with `{ auto: true }`:

```typescript
import { test as base } from '@playwright/test';

export const test = base.extend<{ myTestFixture: string }>({
  myTestFixture: [async ({}, use) => {
    // fixture setup...
    await use('fixture value');
    // fixture teardown...
  }, { auto: true }], // <-- make 'auto' fixture
});
```

Playwright still runs the fixture because it is automatic.

##### Built-in Fixtures

Playwright also provides several fixtures out of the box. The most common one is `page`, which gives you access to a browser page. Two things stand out on the timeline for two tests using `page`:

- Besides the blue bars for the test-scoped `page` fixture, there is a yellow bar for the worker-scoped `browser` fixture. The `page` fixture depends on the `browser` fixture, so Playwright creates that dependency first.
- The second `page` setup is much shorter than the first. Playwright uses some internal optimization to set up subsequent `page` fixtures.

##### Fixture Override

You can override any fixture with another `test.extend()` call. For example, this code overrides the built-in `page` fixture and adds custom setup and teardown around it:

```typescript
import { test as base } from '@playwright/test';

export const test = base.extend({
  page: async ({ page }, use) => {
    // custom page setup...
    await use(page);
    // custom page teardown...
  },
});
```

Notice the `{ page }` dependency inside the override. This is the original Playwright `page` fixture. Playwright creates that original page first, then runs your wrapper around it.

##### Fixture Dependencies

Fixtures can also depend on other fixtures. In this example, `fixtureC` depends on `fixtureA` and `fixtureB`:

```typescript
import { test as base } from '@playwright/test';

export const test = base.extend<{
  fixtureA: string;
  fixtureB: string;
  fixtureC: string;
}>({
  fixtureA: async ({}, use) => {
    await use('A');
  },
  fixtureB: async ({}, use) => {
    await use('B');
  },
  fixtureC: async ({ fixtureA, fixtureB }, use) => {
    await use(`${fixtureA} - ${fixtureB} - C`);
  },
});
```

Playwright sees that `fixtureC` needs `fixtureA` and `fixtureB`, so it sets up both parent fixtures first. Teardown goes in the opposite order.

##### Worker Fixtures

When setup is expensive and can be shared between several tests, use a worker-scoped fixture instead of the default test-scoped:

```typescript
import { test as base } from '@playwright/test';

export const test = base.extend<{}, { myWorkerFixture: string }>({
  myWorkerFixture: [async ({}, use) => {
    // worker fixture setup...
    await use('worker fixture value');
    // worker fixture teardown...
  }, { scope: 'worker' }],
});
```

Both tests run in the same worker, so Playwright creates one `myWorkerFixture` instance and reuses it. There is no worker fixture setup between the two test bodies.

Worker-scoped means "once per worker", not "once per test run". To see the difference, split the two tests into separate files and run with two workers: each worker gets its own `myWorkerFixture`, so the setup runs twice.

##### Putting It Together

You can combine multiple test-scoped and worker-scoped fixtures in the same test. Playwright initializes every required fixture and its dependencies in the correct order. `myTestFixture` is initialized and removed for each test, while `myWorkerFixture` is created once for the worker and reused by both tests.

##### Conclusion

Fixtures are powerful, especially when you keep these principles in mind:

- Scope: per test or per worker?
- Check fixture dependencies and overrides.
- Track fixture durations: slow fixtures can significantly decrease performance.

### 27. Vitaliy Potapov — Why Workers Restart

- Source: https://vitalets.github.io/posts/playwright-in-pictures/why-worker-restarts/
- Retrieved: 2026-08-29
- Firecrawl status: complete

Playwright runs tests in workers. These are separate OS processes started by the test runner. Playwright reuses a worker while it can, but under some conditions it restarts the worker. This matters because the restart takes time, and more importantly, all worker-level hooks and fixtures run again after the restart, increasing the total execution time.

##### Example Setup

One test file with three tests:

```typescript
import { expect, test } from '@playwright/test';

const wait = (ms: number) => new Promise(r => setTimeout(r, ms));

test('first', async () => { await wait(1000); });
test('second', async () => { await wait(1000); });
test('third', async () => { await wait(1000); });
```

The run uses a single worker: `npx playwright test --workers 1`. This example run has no restart. All three tests run in the same worker.

##### Restart After Test Failure

Change the second test to fail. Playwright does not run the third test in the same worker. After a failure, it discards the worker process and starts a new one for the next test. This behavior is documented in Playwright retries guide: a failed test causes the whole worker process to be discarded, and the next test continues in a new worker.

##### The Hidden Cost: beforeAll Runs Again

Add a heavy `beforeAll` hook to the same file:

```typescript
test.beforeAll(async () => {
  await wait(2000);
});
```

The failed test no longer adds only worker restart gap. The run also contains a second execution of `beforeAll`. Worker-scoped fixtures have the same cost. Playwright sets them up for each worker process, so a replacement worker initializes them again.

##### Restart on Project Switch

When the config has multiple projects, Playwright restarts the worker when the next test belongs to a different project than the previous one:

```typescript
import { defineConfig } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'project-a' },
    { name: 'project-b' },
  ],
});
```

The timeline shows a worker restart gap, but this is not failure recovery. The first worker is used for `project-a`, and the second worker is used for `project-b`.

##### Project Switch Repeats beforeAll

Both projects now pay the setup cost. The setup is not shared across projects. Two projects mean two worker processes, and each worker runs its own `beforeAll`.

##### Restart on test.use()

There is another, less obvious case where a worker restarts. If a test file calls `test.use()` with a worker-scoped fixture, Playwright runs that file in a new worker:

```typescript
test.use({ screenshot: 'on' });
test('third', async () => { await wait(1000); });
```

The timeline shows a worker restart, even though there are no test failures or project boundaries. In practice, any override of a worker-scoped fixture via `test.use()` causes a worker restart, which can increase the total test duration.

##### Key Takeaways

- Playwright restarts the worker after every test failure.
- A worker restart takes time to spin a new OS process.
- The larger impact is repeated execution of worker-level hooks and fixtures.
- Project boundaries also create new worker processes, so each project pays its own worker-level setup cost.
- Overriding worker-scoped fixtures via `test.use()` triggers a worker restart.

### 28. Vitaliy Potapov — Fully Parallel

- Source: https://vitalets.github.io/posts/playwright-in-pictures/fully-parallel/
- Retrieved: 2026-08-29
- Firecrawl status: complete

Playwright `fullyParallel` mode is often treated as a simple performance switch. In practice, it changes how the runner schedules work, which leads to different execution shapes for the same test suite.

##### Example Setup

A minimal suite: `spec1.test.ts` with 1 test, `spec2.test.ts` with 5 tests, `workers = 2`.

##### Non-Fully Parallel

By default, Playwright assigns entire files to workers. Once a worker picks a file, it runs all tests in that file in order.

```bash
npx playwright test --workers 2
```

In this setup, Worker 1 runs the single test from spec1, while Worker 2 executes all 5 tests from spec2. Tests inside a file cannot move to another worker. Even if one worker is idle, it cannot pick up remaining tests from other running files. In practice, the total run time is defined by the longest file, not by the total amount of work.

##### Fully Parallel

With `--fully-parallel` enabled, Playwright schedules individual tests instead of files. File boundaries stop mattering. Workers take the next available test.

```bash
npx playwright test --workers 2 --fully-parallel
```

With the same setup, the 5 tests from spec2 are split across both workers, keeping the timeline balanced. The total run time drops from **5.6s** to **3.5s**.

This shifts the execution model. It now follows individual tests instead of the longest file.

##### Is Fully Parallel Always Faster? No.

Fully parallel mode may be slower if tests rely on heavy worker hooks or worker fixtures. A heavy `beforeAll` hook added to spec2:

```typescript
test.beforeAll(async () => {
  await expensiveSetup()
});
```

Running the tests without fully parallel: the `beforeAll` setup cost is paid once in Worker 2 and reused across all tests in that file.

Running the same suite with `--fully-parallel`: `beforeAll` runs twice, once per worker. As the number of workers grows, the setup is repeated more times. Total run time increases from **15s** to **20s** after enabling fully parallel mode.

When setup dominates test time, `--fully-parallel` makes the run slower.

##### Key Takeaways

- By default, Playwright runs tests per file: files are split across workers, tests inside a file run sequentially.
- With fully parallel mode, tests are split across workers and run independently.
- Fully parallel mode can slow tests down. Check your test distribution and setup before enabling it.

The environment I am working with can be unstable sometimes. To ensure I do not have false negative tests, I need to rerun the failed checks. Playwright makes this easy by allowing you to pass `--retries` followed by the number of retries.

##### Skipping certain tests if retried

The problem was that certain checks should not be retried when running the automation suite (1500 checks in total). The solution was found in `testInfo`. `testInfo` provides useful information about currently running specs. One of its properties is `retry`, which returns the current retry number (0 for the initial run). If `retry` is greater than 0, the test can just skip itself.

When the test is run: the test fails because 1 is not 2. `testInfo` is updated, and the `retry` property now equals 1. The `if` block skips the test on retry. For better readability, you can write the `if` block as `if (testInfo.retry > 0)`.

##### Adding a delay to your test if retried

If your environment is acting up and cannot handle the load, you can add artificial waits with `.retry`. You can increase the wait based on the retry number.

When the test is run: the initial run does not wait for anything because 0 * 2 = 0. If the test fails, the first retry will wait for 2 seconds because 1 * 2 = 2, and so on.

##### Cleaning up data after test retries

`testInfo.retry` can also be used to clean up data. For example, if you want to delete certain data created by retries but keep what was created by the initial run, the retry number lets you branch the cleanup logic.

##### You are only limited by your imagination

You can utilize `testInfo.retry` for things like names or IDs of the data you create. This might help you track what data was created during which retry.

From there [Sergei Gapanovich](https://playwrightsolutions.com/author/sergei/) took the idea and built the code which powers the feature-map package.

##### Overview: feature-map package

The feature-map package is a bare bones library that allows you to create a yaml file with different actions/features within a website and add a `true` or `false` value to indicate if there is automation coverage against that feature.

The primary purpose of this tool was to create a map of all the different actions that can be made within a web application through the UI, and map them out. Based on this map, you can indicate if there is any automation coverage that exercised the functionality. Through this functionality you can track overall test coverage for the UI that you are testing. Think about it as a measuring stick: create a list of items, and use this to measure progress against test coverage.

What is nice about this is that it can all be created and maintained through the yaml file which is also committed to the same repository as your test code. As you add automation coverage that covers new actions, you can also update the feature-map with the new coverage, and get feedback on what percentage of the features have any sort of automation around them.

Did you say percentage, as in test coverage percentage? Well, sort of. It is very difficult to put such an absolute percentage on this unknown wicked problem. When talking about a percentage here, it is identifying what the things we want to measure against are (the actions throughout the website), adding them to the yaml, and measuring if there is any coverage against those actions.

##### Implementing the feature-map package

Install the package into the project from the root of the directory, then create a yaml file in the repository that will be the feature map. Two key terms to understand yaml files: Collections can be Sequences (lists/arrays) and Mappings (dictionaries/hashes).

- Anytime you see the dash (`-`) it is used to denote a list item or element. At the highest level we use these sequences (lists) to organize our pages in the file.
- `- page: "/auth/login"` defines a new **list** with the URL path "/auth/login".
- `features:` starts a **list** of features associated with the current page.
- `sign in with google: false` is an example of a **mapping** which defines a feature/action named "sign in with google" and sets its value to `false`.

It is important that each list (sequence) ends with a key value pair (mapping).

Next, use the functions from the package in the Playwright test. The feature calculation can be a part of the test run: implement a new project named `calculation` in the playwright config, and make the `ui-tests` dependent on `calculation`. A new spec file for the calculation project checks an environment variable named `CALCULATE_COVERAGE` that is expected to be `true` in order for the `calculateYamlCoverage()` function to run.

With this change the npm library not only logs the output of the coverage in the console but also generates a text file named `coverage-output.txt` that can be easily viewed locally or saved as an artifact in CI for review.

##### Future Improvements and Shortcomings

One area where this tool currently falls short is the ability to easily track test scenarios or cases as a part of the feature map. Currently everything is categorized as `features`.

A future feature could be dynamically scraping the webpage and automatically building out/adding to the featureMap.yml file, acting as a change detector to help ensure that new areas of the system have coverage.

Another shortcoming is keeping the featureMap.yml file up to date with the actual reality of the front end of the website under test. It requires diligence to update the featureMap.yml to match reality. Creating a "what we want to add automation around" phase in a project has been a good cadence of doing a full site check, typically once a quarter.

Another shortcoming: there is only a `true` or `false` value, so it is difficult to communicate the depth of coverage against a certain action. Ideally, functionality not planned for UI automation coverage could have a different status such as `omitted` indicating that we purposely do not want to add automation around this in the UI (maybe it is covered at a lower level) and have that status not count against the overall coverage percentage.

##### Wrap Up

This tool can be really valuable in communicating overall status and coverage of UI automation test coverage. It is all a part of the repository, and can get updated along with UI automation specs as they are committed. It has been useful during code reviews to always check the UI coverage against the featureMap.yml to ensure the file was updated with any changes as necessary.

### 38. Butch Mayhew / Playwright Solutions — apiRequestContext disposed

- Retrieved: 2026-08-29
- Firecrawl status: complete

Within automation tests at work, two errors were encountered when using the `await page.route()` functionality:

```
Error: apiRequestContext.fetch: Request context disposed
Error: apiRequestContext.fetch: Browser has been closed
```

This typically happens when there is a request or a group of network requests that are made within a page, and the test finishes before the API request(s) are complete.

##### Reproducing the issue

An example reproduces every 10 or so runs. Download the repo and run this command to see the failure:

`npx playwright test tests/checkout/checkoutWithRoute.spec.ts --repeat-each 20`

The reason this happens is the network request is not finished even though the test has finished running. Against this application and this API request we are routing, it does not happen very often, but if you are routing multiple requests or if the application is fetching a lot of data, this is more likely to happen.

##### Tips to prevent or fix these errors

###### Check your awaits in your test file

First off, make sure you have any browser or network interactions "awaited" properly, e.g. `await homePage.goto()`. If you are not awaiting things properly you could get these errors or different errors depending on what actions are still being done at the test end.

###### Utilize waitForResponse()

Next, use the function `await page.waitForResponse()` before your test ends to ensure all network traffic has responded. With this in place, the test will never fail because a network connection is still open.

###### Make your routes very specific

For a reporting page that fetches all payments, the test ends up routing over 10 API calls that match the following pattern:

```typescript
await page.route("**/payment-intents?**", ...)
```

One solution would be to make the route more verbose, not using regex matchers. For the assertions in the test, only the first 25 requests needed to be loaded. Limiting the amount of requests that get routed through `page.route()` should help with these types of issues:

```typescript
await page.route("**/payment-intents?offset=0&limit=25", ...)
```

Overall these can be frustrating errors to troubleshoot, and resolve, mainly due to network timings of systems we test.

I brought the internet favorite new take to the table, that the Page Object Model is dead in the AI era. Stefan did not blink:

> "If AI is making a mistake, you are not tweaking your AI correctly."

I wanted a fight and got agreement instead, because I have seen zero evidence an agent cannot handle page objects when the rules are written down. The honest confession from my side: we did not arrive at composition gracefully. We hit the inheritance wall, detoured through mixins, collected runtime collisions, and only then found components. That whole scar story is in the act, next to the ESLint setup Stefan says changed his entire life.

##### Round 4: Bring a Scaffold to Every Project

Stefan claim: a good framework should be built from scratch exactly once. Then it becomes a scaffold, a product you carry into every new project, and a week of setup turns into hours. But he draws a hard line on how you are allowed to use one:

> "Do not just download someone else's scaffold and copy paste without understanding it."

I build and sell a scaffold, and my first guest just told everyone not to blind-copy scaffolds. He is right, and that is exactly why I agreed. A scaffold is a template that carries your lessons, not a substitute for understanding them.
