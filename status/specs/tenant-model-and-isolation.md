## 1. Original Kiro intent

Close the security gap left by `iam-roles-and-keycloak-login`, where the JWT `tenant_id` claim was informational only. Model `Tenant` as a full, enterprise-grade DB entity owned by a new Spring Modulith module `tenant` (package `lab.paymentquality.tenant`), exposing a PUBLIC API (`TenantResolver`, `TenantContext`, `TenantReference`, `TenantResolutionException`) that the `merchant` module consumes — never importing `tenant.internal.*`. Add a `tenants` table (Flyway, new `db/migration/tenant` location) and a `merchants.tenant_id` FK column (backfilled to a seeded `PLACEHOLDER_TENANT_ID` default tenant). Classify principals as platform-scoped vs tenant-scoped purely by the resolved tenant's `tenant_type` column (`PLATFORM`/`STANDARD`) — never by authority. Enforce a Tenant_Boundary_Check on merchant list/detail/create/status-change endpoints, additive on top of existing authority and merchant-scope checks: cross-tenant reads → masked `404`, cross-tenant writes → `403`. Payment orders get isolation *transitively* through the merchant (`PaymentOrderController` needs no code change per the design's own analysis). One controlled REST contract addition: optional `tenantReference` field on `POST /api/merchants` (required for platform-scoped principals, ignored for tenant-scoped). Optional `?tenantId=` filter on `GET /api/merchants` for platform-scoped principals. 7 Resolved Decisions fix the ambiguous points (natural-key claim mapping, data-driven classification, 404-vs-403 split, suspension scope, explicit platform tenant assignment, Flyway module/location ownership, realm-literal coupling). Work is sequenced Wave 0 (tenant module foundation) → Wave 6 (optional jqwik property tests P1–P6), with a checkpoint after every wave and a final full-regression checkpoint.

## 2. Current implementation summary

All 7 required waves (0–5) plus the optional Wave 6 are present in code on this branch, matching the design closely:

- `tenant` module: `package-info.java`, PUBLIC types (`TenantReference`, `TenantContext`, `TenantResolutionException`, `TenantResolver`), and `internal/{domain,infrastructure,application}` (`Tenant`, `TenantStatus`, `TenantType`, `JpaTenantRepository`, `TenantResolverService`) all exist under `apps/backend/src/main/java/lab/paymentquality/tenant/`.
- Flyway: `db/migration/tenant/V0.1__create_tenants.sql` (renamed from the design's `V1`) creates `tenants` + seeds `PLATFORM_TENANT`/`TENANT_ALPHA`/`PLACEHOLDER_TENANT_ID`; `db/migration/merchant/V1.1__add_tenant_to_merchants.sql` (renamed from `V2`) adds the nullable→backfill→NOT NULL→FK→index sequence. `application.yml` and `application-test.yml` both list `classpath:db/migration/tenant` first.
- `Merchant` entity has a plain `UUID tenantId` FK column (no cross-module `@ManyToOne`), a 4-arg `create(...)` factory, and `getTenantId()`.
- `JpaMerchantRepository` has `findByMerchantIdAndTenantId` and `findAllByTenantIdOrderByCreatedAtDescMerchantIdAsc` (uses `Pageable`, a minor deviation from the design snippet's `PageRequest` parameter type — functionally equivalent).
- Merchant-layer exceptions `TenantBoundaryViolationException`, `MissingTenantReferenceException`, `UnresolvableTenantReferenceException` exist under `merchant/internal/domain`.
- `CreateMerchantRequest` has the additive optional `tenantReference` field (plus a backward-compatible 2-arg constructor).
- `MerchantService` is tenant-aware for create/findById/listFirstPage/activate/suspend, using constructor-injected `TenantResolver`.
- `MerchantController` resolves `TenantContext` per request (post `@PreAuthorize`), wires the `?tenantId=` filter, and delegates to tenant-aware service methods.
- `MerchantExceptionHandler` maps `TenantResolutionException`/`TenantBoundaryViolationException` → 403 and `MissingTenantReferenceException`/`UnresolvableTenantReferenceException` → 400, non-disclosing.
- Test suite: `TenantResolverServiceTest`, `MerchantServiceTenantTest`, `JpaMerchantRepositoryTenantTest`, `MerchantControllerTenantSecurityTest`, `TenantModuleTest`, `TenantIsolationIT` (9 scenario methods matching the design's 9 scenarios), and `TenantIsolationPropertyTest` (10 property methods covering P1–P6, some split into sub-properties 3a–3d, 6a–6b) all exist and are confirmed present in the working tree.
- Module boundary confirmed clean: `grep -rn "lab.paymentquality.tenant.internal" apps/backend/src/main/java/lab/paymentquality/{merchant,payment}` returns no matches.
- **One documented public-API deviation**: `TenantResolver` was extended beyond the design with `UUID resolveTenantId(TenantReference tenantReference)` (Wave 2) to let `MerchantService` resolve a platform-supplied `tenantReference` string without importing `tenant.internal.*`. This is recorded in `.codex/current-state.md` under "Resolved Spec Gap" and in `.codex/tenant-model-and-isolation.md` as an explicitly anticipated, acceptable extension.

## 4. Acceptance criteria gaps

- **Requirement 8 (transitive payment-order isolation)**: the design's own analysis (§"Payment Order Transitive Isolation — Design Decision") concludes no `PaymentOrderController` code change is required, and this is honored (no payment module source file was touched, confirmed via `.codex/current-state.md` boundary checks in every wave). However, there is **no dedicated REST-level test that exercises actual payment-order endpoints cross-tenant** — `TenantIsolationIT` covers only merchant endpoints, and the Wave 6 P4 property test exercises `MerchantService.activate(...)`, not a payment order. The transitive guarantee rests on the untouched, pre-existing `merchant_id` JWT-claim check in `PaymentOrderController`, which was already covered by pre-existing payment order tests (outside this spec) — but there is no isolation-specific regression test proving Requirement 8.1–8.3 end-to-end for payment orders under the new tenant model. This is a real, if minor, acceptance-criteria gap for Requirement 8, acceptable given the design's own reasoning but worth flagging.
- **Requirement 10 (isolation matrix)**: satisfied by `TenantIsolationIT`'s 9 scenarios for the merchant rows of the matrix; the payment-order rows of the matrix (last two rows) are not directly exercised by any tenant-specific test, for the same reason as above.
- All other acceptance criteria (Requirements 1–7, 9) have direct code and test evidence as itemized in §3.
