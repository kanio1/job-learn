## 1. Original Kiro intent

Introduce a realistic multi-role IAM foundation and a real Keycloak OIDC login flow for the Dashboard, as a brownfield extension with **no backend Java source changes and no REST contract/authority changes**. Five named Composite_Roles (`PLATFORM_ADMIN`, `TENANT_ADMIN`, `MERCHANT_MANAGER`, `SUPPORT_AGENT`, `READ_ONLY_USER`) are modeled in Keycloak as composite realm roles over the ten existing raw `Realm_Authority_Role`s, plus a `tenant_id` protocol mapper and one deterministic Test_User per role. On the frontend: a single-source `rbacMatrix` capability table, a `useAuthorization` composable, server-side `SessionUser` derivation (roles/tenantId/merchantId, token never leaves the server), a 401-vs-403 reaction layer (`useAuthError` + `auth.global.ts`), a `/forbidden` page, login-page extensions, role-aware sidebar/Overview rendering, role-gated merchant/payment action controls, a logout-control test id, and confirmation that `Authorization` headers are always masked in learning panels. All test sub-tasks (marked `*`) are optional and excluded from the MVP cut; no Playwright files are created by this spec (conceptual coverage only, authored later). Discrepancy A (inert composite-name authorities) was already resolved by the prerequisite `backend-authority-refactor` spec, so task 2 is verification-only.

SUPPORT_AGENT/READ_ONLY_USER still correctly exclude all create/update-status/lifecycle authorities (Req 1.7/1.8 still hold).
- `KeycloakRealmRoleConverter.java` uses the explicit `KNOWN_ROLES` allowlist (delivered by `backend-authority-refactor`, since extended by later specs) — unknown/composite-name claims are silently ignored (fail-closed); no inert `platform:<NAME>` authority is produced.
- `apps/frontend/app/utils/rbacMatrix.ts` is the single-source `CompositeRole`/`Capability`/`rbacMatrix` constant; extended beyond the original 8 capabilities with later-spec capabilities (audit log, users, notes, tenant settings) — additive, does not alter the original 8.
- `apps/frontend/app/composables/useAuthorization.ts` derives `roles`/`can`/`hasRole` purely from `useUserSession().user` and `rbacMatrix`, with no token logic.
- `apps/frontend/server/routes/auth/keycloak.get.ts` decodes the access-token payload without Node `Buffer`, derives `SessionUser { username, email, roles (intersected with the 5 composite names), tenantId, merchantId }` into the non-secure session partition, keeps `accessToken` only in `secure`, and restores the captured `auth_redirect` cookie target (fallback `/admin/merchants`).
- `apps/frontend/app/composables/useAuthError.ts` implements the deterministic, mutually exclusive 401→`/login`, 403→`/forbidden` reaction; `apps/frontend/app/middleware/auth.global.ts` captures the intended route via `?redirectTo=` before redirecting unauthenticated visitors, treats `/forbidden` as authenticated-only, and lets `/login` pass through / bounce logged-in users to `/admin/merchants`.
- `apps/frontend/app/pages/forbidden.vue` has `data-testid="forbidden-page"`, a single `<h1>`, `data-testid="forbidden-home-link"`, and text (not color) stating the authenticated-but-forbidden condition.
- `apps/frontend/app/pages/login.vue` has `data-testid="auth-required-surface"`, `login-control`, `auth-error-message` (shown on `?error=keycloak`), moves focus to the login button on mount, and captures `redirectTo` into a cookie before navigating to `/auth/keycloak`.
- `apps/frontend/app/layouts/dashboard.vue` filters sidebar links (`nav-link-overview`, `nav-link-merchants`, `nav-link-payment-orders`, plus later-spec links) through `useAuthorization().can`, mirrors the same filter into `UDashboardSearch` groups.
- `apps/frontend/app/pages/index.vue` (Overview) gates the Platform Summary section on `canReadOverviewSummary`, merchant cards on `canReadMerchants`, payment cards/recent-orders on `canReadPaymentOrders` (`canReadMerchantPayments || canReadPlatformPayments`), and `fetchSummary()`/`fetchRecentOrders()` skip their backend calls entirely when the governing capability is absent — this is task 9.2, whose Kiro checkbox is unchecked but whose code and behavior fully satisfy Requirement 9.2/9.7.
- `apps/frontend/app/components/merchant/CreateMerchantForm.vue` and `MerchantTable.vue` gate create/activate/suspend controls on `canCreateMerchant`/`canUpdateMerchantStatus` with accessible `aria-label` explanations when disabled — task 10.1, unchecked box, code confirms implementation.
- `apps/frontend/app/components/payment/CreatePaymentOrderForm.vue` (`data-testid="action-create-payment-order"`, gated on `canCreatePaymentOrder`) and `apps/frontend/app/components/shared/PaymentOrderLifecycleActions.vue` (`action-lifecycle-authorize/capture/cancel/refund`, gated on `canRunLifecycle`) — task 10.2, unchecked box, code confirms implementation.
- `apps/frontend/app/components/AppUserMenu.vue` has `data-testid="logout-control"` on the sign-out trigger.
- `apps/frontend/app/components/shared/HeaderKeyValuePanel.vue` and `ApiDebugPanel.vue` both mask any `Authorization`-keyed header (case-insensitive) to the fixed `Bearer ••••••••` placeholder before rendering; `apps/frontend/server/utils/backendApi.ts` forwards only an explicit allow-list (`ETag`, `Cache-Control`, `Vary`, `X-Correlation-ID`, `Location`, `Accept-Patch`, `Allow`) and never `Authorization`.
