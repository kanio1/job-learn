### TD-2A — RESOLVED 2026-07-12 (10 of 21 tests fixed, 0 regressions)

Two distinct, now-confirmed root causes, fixed together because both are pure test-infrastructure/test-mock defects discovered via the same investigation and both needed for the affected spec files to reach a stable state:

**TD-2A-1 (8 tests): default 5000ms Playwright assertion timeout too tight for this project's `nuxt dev` webServer.**
Measured first-render latency for a fresh `/admin/merchants*` navigation (session fetch → middleware → Suspense resolution → component mount) is consistently ~4.1–4.6s in isolation (confirmed via a temporary diagnostic probe spec, removed after use), and regularly exceeds 5s under this machine's default worker parallelism (16 workers sharing one dev server, confirmed via `nproc`=32). Proof: rerunning the failing 8 files serially (`--workers=1`) dropped 21→13 failures with zero code changes — pure contention removal. `ui/command-palette.spec.ts` already worked around this per-assertion with an explicit `{ timeout: 15000 }` on the same "Merchants" heading other tests check with the default. **Fix**: `apps/frontend/playwright.config.ts` — added project-wide `expect: { timeout: 15_000 }` (see inline comment for full justification). Fixed: `foundation.spec.ts` (1), `payment-status-polling.spec.ts` (2, one is borderline-flaky under full-82-test contention — passes reliably in isolation/smaller batches), `rbac/merchant-risk-flag.spec.ts` (2), `auth-deny.spec.ts` "authenticated identity..." (1), `payment-orders-panel.spec.ts` "renders payment summary..." + "renders forbidden state..." (2).

**TD-2A-2 (2 tests): `mockAuthenticatedSession()` test helper omits the `roles` array, so `useAuthorization()`'s fail-closed empty-roles default hides every capability-gated button.**
`infra/keycloak/realms/payment-quality-realm.json` confirms the real `platform.operator` user (the helper's default username) is assigned realm role `PLATFORM_ADMIN`, which per `app/utils/rbacMatrix.ts` grants `canCreateMerchant`/`canUpdateMerchantStatus`/etc. The mock never replicated this — `{ loggedIn: true, user: { username } }` has no `roles`, so `useAuthorization()` (`app/composables/useAuthorization.ts`) computes an empty roles array and every capability is `false`. This hid the "Create merchant" and "Activate/Suspend" buttons entirely for any test using the bare helper. **Fix**: `apps/frontend/tests/e2e/merchant-support.ts` — `mockAuthenticatedSession(page, username, roles = ['PLATFORM_ADMIN'])`; the one call site that deliberately wants a no-authority session (`auth-deny.spec.ts`'s "authenticated identity without merchant authority" test, username `'merchant.denied'`) was updated to pass `roles: []` explicitly to preserve its intended denial scenario. Fixed: `merchant-create.spec.ts` "create-merchant-form data-testid..." + "activate-merchant-button data-testid... for a pending merchant" (2).

Targeted validation: the exact 8 originally-failing spec files rerun with both fixes → **11 failed / 18 passed** (down from 21/61). Full 101-test chromium baseline rerun → **12 failed / 70 passed** (1 extra — `payment-status-polling.spec.ts:52` reappeared under full-suite 16-worker contention; confirmed flaky, not a new defect: reruns green in isolation, `3 passed` in 19.6s). Frontend `typecheck` and `test:unit` (532/532) both green after the fix, confirming no regression. **Zero new failures introduced anywhere in the 101-test suite.**

### TD-2B — NOT FIXED (7 tests): merchant status contract mismatch, `'PENDING'` vs real backend `'DRAFT'`

**CONFIRMED**, high-confidence, evidenced production defect — this is the genuine substance behind the prior session's rejected hypothesis, now visible once TD-2A stopped masking it.

- Real backend: `apps/backend/src/main/java/lab/paymentquality/merchant/internal/domain/MerchantStatus.java` — enum is `DRAFT, ACTIVE, SUSPENDED`. `MerchantMapper.toResponse()` serializes via `.name()`, so the wire value for a freshly-created merchant is literally `"DRAFT"`.
- Frontend uses `'PENDING'` instead of `'DRAFT'` in **7 production locations**: `app/composables/useMerchantsApi.ts:19` (`merchantStatusSchema` Zod enum — a real `DRAFT` merchant would currently **fail Zod validation entirely** against a real backend, breaking the whole merchant list fetch, not just a button), `app/components/merchant/MerchantTable.vue:42,66,129` (type union, badge-color-case, and the `v-if` condition that shows the Activate button), `app/pages/admin/merchants/index.vue:199` (status filter dropdown `value: 'PENDING'`), `app/components/shared/BusinessStatusBadge.vue:27` (status→label/color map keyed by `PENDING`; a real DRAFT merchant would render as "Unknown" badge, not "Pending"). Also affects test files that must track the real contract: `app/components/shared/BusinessStatusBadge.test.ts:18`, `tests/e2e/visual-regression.spec.ts:26`.
- Test-mock symptom: `tests/e2e/merchant-support.ts`'s `mockMerchantApi()` `/activate` handler correctly requires `merchant.status === 'DRAFT'` (matching the real backend) before allowing the transition; `merchant-create.spec.ts:139` and `merchant-lifecycle.spec.ts:26,43` seed via `merchant(ref, 'PENDING')` — an invalid literal not even in the mock's own `Merchant['status']` type union (`'DRAFT'|'ACTIVE'|'SUSPENDED'`) — so the mock's own `/activate` handler rejects the transition (409), and "ACTIVE" never appears.
- **Open question requiring a product decision, not a guess**: `merchant-create.spec.ts:20` already asserts `getByText('DRAFT', { exact: true })` after creating a merchant — i.e. the test's original author expected the **raw enum value** "DRAFT" to be literally visible on the page, not a friendly "Pending" label. Whether the correct product behavior is (a) display the technical value `DRAFT` verbatim, or (b) display a friendlier label (e.g. "Pending"/"Draft") while fixing only the underlying *value* to `DRAFT`, is a UX decision this audit will not guess at. **Recommended next action**: fix all 7 production locations' status *value* to `DRAFT` (required regardless — the Zod-rejection risk against a real backend is severe), keep investigating the exact intended *display label* before touching `BusinessStatusBadge.vue`'s label text, and fix the 3 test-mock call sites' literal from `'PENDING'` to `'DRAFT'`.
- Affected tests: `merchant-create.spec.ts:4` (modal "Create" submit button — also gated by `canCreateMerchant`, now true, but the button did not become clickable in one observed run, needs re-check once the value fix lands), `:23`, `:52`, `:81` (same "Create merchant"/modal flow), `merchant-lifecycle.spec.ts:4,23,39` (Activate/Suspend flow, direct 409 rejection confirmed for `:23`/`:39`).
