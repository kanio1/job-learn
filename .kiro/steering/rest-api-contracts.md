# REST API Contracts — Payment Quality Engineering Lab

## Core Principle

The API surface is stable. Contracts are not changed unless a Kiro Spec explicitly requires it.
Every header, status code, and error shape below is tested — do not silently drop them.

---

## Required Headers by Operation Type

### Create operations (POST that creates a resource)

| Header | Direction | Rule |
|---|---|---|
| `Idempotency-Key` | Request (required) | Client-generated UUID or opaque string. De-duplicates the operation. |
| `Content-Type: application/json` | Request | Required for all POST/PATCH with a body. |
| `Location` | Response (201 only) | URI of the created resource. Must be present on a true 201. |
| `ETag` | Response | Version marker of the created/replayed resource. |
| `Vary: Authorization, Idempotency-Key` | Response | Must be present on create responses. |
| `Cache-Control: no-store` | Response | Sensitive payment responses must not be cached. |
| `X-Correlation-ID` | Response | Tracing ID generated by the backend for every response. |

### Read operations (GET, HEAD)

| Header | Direction | Rule |
|---|---|---|
| `ETag` | Response | Version marker. Used by the client for subsequent If-Match writes. |
| `Vary: Authorization` | Response | Must be present. |
| `Cache-Control: no-store` | Response | Sensitive payment responses. |
| `X-Correlation-ID` | Response | Always present. |

### State-changing lifecycle operations (POST authorize/capture/cancel/refund, PATCH metadata)

| Header | Direction | Rule |
|---|---|---|
| `Idempotency-Key` | Request (required for POST lifecycle) | Unique per intent; same key replays without side effects. |
| `If-Match` | Request (required) | Must carry the ETag from the most recent read or write. |
| `ETag` | Response | New version marker after the state change. |
| `Vary: Authorization, If-Match` | Response | Must be present. |
| `Cache-Control: no-store` | Response | Required. |
| `X-Correlation-ID` | Response | Always present. |

### OPTIONS / discovery

| Header | Direction | Rule |
|---|---|---|
| `Allow` | Response | Lists the HTTP methods allowed on the resource. |
| `Accept-Patch` | Response | Present on resources that accept PATCH. Value: `application/merge-patch+json`. |
| `X-Correlation-ID` | Response | Always present. |

## Status Codes

### Success

| Code | Meaning | When used |
|---|---|---|
| `200 OK` | Success | GET, HEAD, successful lifecycle action, idempotent replay of create. |
| `201 Created` | Resource created | First successful POST that creates a resource. Includes `Location`. |
| `204 No Content` | Success, no body | OPTIONS responses. |

### Client Errors — Problem Contract

All `4xx` responses use `Content-Type: application/problem+json`.

| Code | Error type | Trigger |
|---|---|---|
| `400 Bad Request` | `validation` / `malformed_json` / `malformed_if_match` | Invalid request body, malformed JSON, malformed ETag format. |
| `401 Unauthorized` | — | Missing or invalid bearer token (enforced at proxy/security layer). |
| `403 Forbidden` | `forbidden` | Valid token but insufficient authority or merchant scope mismatch. |
| `404 Not Found` | `not_found` | Resource does not exist (masked: same shape for "not yours" and "not found"). |
| `405 Method Not Allowed` | — | HTTP method not supported on the endpoint. |
| `406 Not Acceptable` | — | Client sent `Accept: application/xml` or unsupported Accept header. |
| `409 Conflict` | `idempotency_conflict` | Same `Idempotency-Key` with different request payload. |
| `412 Precondition Failed` | `precondition_failed` / `concurrency_conflict` | Stale `If-Match` / version mismatch / optimistic lock failure. |
| `415 Unsupported Media Type` | `unsupported_media_type` | Wrong `Content-Type` (e.g. `text/plain` instead of `application/json`). |
| `422 Unprocessable Entity` | `invalid_transition` / `authorization_expired` / `capture_exceeds_authorized` / `refund_exceeds_captured` | Business rule violation on lifecycle action. |
| `428 Precondition Required` | `precondition_required` | `If-Match` header missing on a write that requires it. |
| `429 Too Many Requests` | — | Rate limiting (future; document the gap if not yet implemented). |

### Server Errors

| Code | Meaning |
|---|---|
| `500 Internal Server Error` | Unexpected backend error. |
| `503 Service Unavailable` | Backend unreachable (returned by the Nuxt proxy when `$fetch` cannot reach the backend). |

## Problem+JSON Shape

All `4xx` error responses use `application/problem+json` (RFC 7807 / RFC 9457):

```json
{
  "type": "https://example.com/problems/validation",
  "title": "Validation Error",
  "status": 400,
  "detail": "amountMinor must be a positive integer",
  "instance": "/api/merchants/abc/payment-orders"
}
```

- `type` — URI identifying the problem type. May be `about:blank` for generic errors.
- `title` — Short human-readable summary. Does not change between occurrences.
- `status` — HTTP status code (mirrors the response status).
- `detail` — Human-readable explanation specific to this occurrence.
- `instance` — URI of the specific resource or request that triggered the error.
- Extension members are allowed and must be preserved (use `.passthrough()` in Zod schemas).

**Never** expose bearer tokens, passwords, internal stack traces, or personal data in `detail` or extension members.

## Idempotency Rules

- `Idempotency-Key` is required on: `POST /payment-orders`, `POST /{id}/authorize`, `POST /{id}/capture`, `POST /{id}/cancel`, `POST /{id}/refund`.
- Missing key → `428` with `precondition_required`.
- Same key + same payload → `200` with the original response body and ETag (replay).
- Same key + different payload → `409` with `idempotency_conflict`.
- Key format: opaque string, max 255 characters. UUID v4 is the recommended format.

---

## ETag / If-Match Rules

- Every `PaymentOrder` resource carries an `ETag` header derived from its version counter.
- **Read before write**: always fetch the current ETag before a lifecycle action or PATCH.
- `If-Match` is required on: `POST /{id}/authorize|capture|cancel|refund`, `PATCH /{id}`.
- Missing `If-Match` → `428 Precondition Required`.
- Stale `If-Match` (version mismatch) → `412 Precondition Failed`.
- After a successful write, the response carries a new `ETag`. Update the stored version marker.
- ETag values are opaque strings wrapped in double quotes: `"3"`. Do not parse the internal value.

---

## Vary Header Rules

The `Vary` header tells caches which request headers affect the response:

| Endpoint type | Vary value |
|---|---|
| Create payment order | `Authorization, Idempotency-Key` |
| Read payment order / list / summary / history | `Authorization` |
| Lifecycle actions / PATCH | `Authorization, If-Match` |

---

## Content Negotiation

- All endpoints consume and produce `application/json`.
- The metadata PATCH endpoint additionally accepts `application/merge-patch+json`.
- Sending an unsupported `Content-Type` → `415 Unsupported Media Type`.
- Requesting an unsupported `Accept` type (e.g. `Accept: application/xml`) → `406 Not Acceptable`.

---

## Correlation ID

- Every response includes `X-Correlation-ID` for distributed tracing.
- Generated by the backend per-request.
- Forwarded by the Nuxt proxy to the browser via `setHeader`.
- Must be displayed in HTTP learning panels and preserved in error lab captures.

---

## Frontend Proxy Responsibilities

`server/utils/backendApi.ts` is the single place that:
1. Attaches the bearer token server-side (from `nuxt-auth-utils` session).
2. Forwards `If-Match`, `Idempotency-Key`, `X-Correlation-ID` request headers to the backend.
3. Forwards these response headers to the browser: `ETag`, `Location`, `Vary`, `X-Correlation-ID`, `Cache-Control`, `Accept-Patch`, `Allow`.

The browser **never** holds the bearer token. Client-side composables read forwarded headers via `$fetch.raw` (which exposes `response.headers` and `response.status`).

## Error Lab Supported Scenarios

The Error Lab page must support exactly these scenarios — no more, no less:

| Status | Trigger method |
|---|---|
| 400 | Submit malformed or invalid request body |
| 401 | Call a protected route without a valid session |
| 403 | Use a token that lacks the required authority |
| 404 | Request a non-existent resource ID |
| 406 | Send `Accept: application/xml` |
| 409 | Repeat an `Idempotency-Key` with a different payload |
| 412 | Send a stale `If-Match` (outdated ETag) |
| 415 | Send wrong `Content-Type` (e.g. `text/plain`) |
| 428 | Omit `If-Match` on a lifecycle action |
