# Effective Java SDET Compass

Use this matrix to translate Effective Java ideas into Senior QA Automation decisions for REST API tests, Spring tests, Mockito tests, AssertJ assertions, and JDK 25 code.

| Effective Java topic | QA Automation meaning | REST Assured example | Spring test example | Mockito/AssertJ example | Common anti-pattern | Preferred modern Java/JDK 25 pattern |
| --- | --- | --- | --- | --- | --- | --- |
| Static factories | Name test data intent clearly | `PaymentRequest.validCardPayment()` | `MerchantRequest.activeMerchant()` in MVC fixture | `assertThat(request).isEqualTo(validRequest())` | Ambiguous constructors with many strings | Named factories plus records/builders |
| Builder pattern | Make scenario setup explicit | `PaymentPayloadBuilder.valid().withAmount("10.00")` | `CreateMerchantCommandBuilder.active()` | Assert built values with AssertJ extracting | Huge constructor calls in tests | Immutable builder output, defaults visible |
| Dependency injection | Make code testable without hidden resources | Inject `RequestSpecification` | Constructor-inject service into controller | Mock external boundary, not values | Hardcoded clients, static state | Constructor injection, small public API |
| Utility classes | Prevent accidental instantiation | `JsonPayloads` private constructor | `MvcJson` private constructor | Assert helper final class | Utility class with public constructor | `final class` + private constructor |
| Avoid unnecessary objects | Keep fast tests and clean fixtures | Reuse configured spec safely | Reuse `ObjectMapper` from Spring context | Avoid rebuilding expected lists in loops | Per-assertion heavyweight setup | Shared immutable fixtures, local mutable data only |
| Obsolete references | Avoid cross-test pollution | No mutable global payload map | No static mutable request object | Fresh builders per test | Static mutable fixture modified by tests | `List.of`, records, builder per scenario |
| try-with-resources | Close IO/test resources reliably | Load fixture files safely | Manage temp files in integration tests | Assert thrown exception if resource fails | Leaked streams/connections | try-with-resources and explicit cleanup |
| equals/hashCode | Stable comparisons and captors | Compare DTO response records | Compare controller response model | `eq(expectedCommand)`, `ArgumentCaptor<T>` | Identity assertions for value objects | Records or correct value implementations |
| toString | Useful diagnostics without leaking secrets | Mask `Authorization` and card data | Mask request DTO diagnostics | Assert no sensitive data in message | Logging token/PAN/CVV | Explicit safe `toString` or record caution |
| Avoid clone | Make copies predictable | `builder.from(existing)` | Copy command through constructor | Assert original unchanged | `clone()` on mutable fixtures | Copy factory, copy constructor, builder |
| Comparable/Comparator | Sort expected API collections clearly | `Comparator.comparing(PaymentDto::createdAt)` | Assert sorted response | `containsExactlyElementsOf(sorted)` | Sorting by stringly-typed magic | `Comparator.comparing().thenComparing()` |
| Minimize visibility | Reduce test support API surface | Private REST execution helper | Package-private test fixtures | Only expose assertion entry points | Public mutable helpers | Private methods, package-private support, final classes |
| Immutability and defensive copies | Prevent flaky shared test data | Payload record copies `metadata` | DTO copies list fields in compact constructor | Assert mutation of source does not affect DTO | Exposed mutable list | Records plus `List.copyOf` / `Map.copyOf` |
| Composition over inheritance | Reuse without fragile test hierarchies | Client composed with auth/spec helper | Controller test composes fixtures | Assertion helper composed from AssertJ | Deep base test classes | Small composed helpers and fixtures |
| Interfaces as types | Mock stable boundaries | `PaymentGatewayPort` | Mock service port in `@WebMvcTest` | `@Mock PaymentService` | Interface for constants only | Interfaces for roles, enums for constants |
| Sealed/record models | Represent closed API outcomes | `sealed interface PaymentResult` | Controller maps result variants | Assert variant with `isInstanceOfSatisfying` | Tagged DTO with `type` plus nullable fields | Sealed interface + records |
| Generics/no raw types | Preserve compile-time test safety | `TypeRef<List<PaymentResponse>>` | `TypeReference<PageDto<MerchantDto>>` | `ArgumentCaptor<Command>` | Raw `List`, unchecked cast | Generic methods, typed captors |
| Prefer lists to arrays | Easier assertions and API modeling | Extract `List<PaymentResponse>` | Response DTO uses `List<Item>` | AssertJ collection assertions | `Payment[]` for normal JSON collection | `List<T>`, immutable copies |
| PECS | Flexible reusable test helpers | Helper accepts `List<? extends RequestDto>` | Assertion consumes `Collection<? extends ErrorDto>` | Generic assertion helper | Overly rigid helper signature | Producer extends, consumer super |
| Enums | Avoid stringly typed states | `PaymentStatus.AUTHORIZED.apiCode()` | `MerchantStatus.ACTIVE` in MVC test | Assert enum field, not ordinal | Status as raw string everywhere | Enum with explicit API code field |
| EnumSet/EnumMap | Model flags and mappings safely | Allowed transitions as `EnumSet` | Error mapping by enum | Assert map contains expected enum keys | Bit flags, ordinal-indexed arrays | `EnumSet`, `EnumMap` |
| Annotations | Make test intent discoverable | `@Tag("contract")` | `@WebMvcTest(PaymentController.class)` | `@Captor` typed captor | Naming conventions only | JUnit/Spring annotations with clear names |
| Lambdas/method references | Reduce noise without hiding intent | `then().body("items", hasSize(2))` helpers | `jsonPath` assertions via helper | `extracting(PaymentDto::id)` | Anonymous classes in tests | Method references when clearer |
| Streams judiciously | Keep assertions readable | Filter response items by status | Map validation errors to fields | AssertJ `filteredOn` instead of complex streams | Long side-effecting stream pipeline | AssertJ extracting/filtering or named helpers |
| Parameter checks | Fail fast in test support | Builder rejects null amount if invalid for scenario | Test helper checks required MVC path | Assert exception message | NPE far from source | `Objects.requireNonNull`, validation in records |
| Empty collections | Remove null handling in tests | Empty `errors()` list | Empty `items()` page response | `assertThat(errors).isEmpty()` | Returning null collections | `List.of()` and immutable empty collections |
| Optional returns | Model absence at boundaries | `findPayment(id)` returns `Optional` in client wrapper | Service lookup returns `Optional` | AssertJ `isPresent` / `isEmpty` | Optional fields/parameters everywhere | `Optional<T>` return only when useful |
| Exceptions | Express failure at right abstraction | Client throws API assertion failure with context | Controller maps domain exception | AssertJ `assertThatThrownBy` | Swallowing exceptions | Standard exceptions, useful safe messages |
| Concurrency | Avoid flaky parallel tests | Worker-isolated data | Separate test contexts only when needed | No shared mutable mocks across tests | Static mutable test state | Immutable data, per-test setup, documented thread safety |
| Serialization caution | Avoid Java serialization by default | JSON DTOs through Jackson | MVC JSON contract tests | Assert serialized JSON fields | Java serialization for API fixtures | Records, Jackson DTOs, explicit JSON contracts |

Use the matrix as a compass, not a script. Always adapt to repository conventions and the exact risk under test.
